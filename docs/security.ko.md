# 보안 강화 모드

English: [Security hardening mode](security.md)

웹 터미널, root 권한 상승, 파일 탐색기처럼 보안에 민감한 기능을 확인을 한 번 더 거친 세션에서만 쓰게 합니다. 열어 둔 브라우저나 빼앗긴 세션 쿠키, 새어 나간 비밀번호만으로는 그 기능을 쓰지 못하게 하는 것이 목적입니다. 기본으로 꺼져 있습니다.

## 보안 정책

관리자가 설정 앱의 "보안 정책" 페이지에서 기능마다 단계를 고릅니다.

| 단계 | 확인 |
|---|---|
| 끔 | 따로 확인하지 않습니다. |
| 비밀번호 재확인 | 그 세션에서 비밀번호를 한 번 더 입력해야 합니다. 로그인할 때 넣은 비밀번호는 치지 않습니다. |
| 2차 인증 | 패스키, 인증 앱(TOTP), 복구 코드 중 하나로 확인해야 합니다. OpenMediaVault의 2차 인증으로 로그인한 세션도 2차 인증을 거친 것으로 봅니다. |

- 파일 탐색기는 기본으로 폴더 보기와 내려받기까지 확인합니다. "파일 탐색기 확인 범위"를 "쓰기·삭제에만"으로 바꾸면 보기와 내려받기는 확인 없이 쓰고, 올리기·폴더 만들기·이름 바꾸기·옮기기·삭제·휴지통 작업 전에만 확인합니다. 범위를 바꾸려면 그 단계를 거친 세션이어야 합니다.
- 같은 페이지에서 [패스키로 로그인](passkey-login.ko.md)의 만료 기간도 고릅니다.
- 확인은 그 세션에 남습니다. 로그아웃하거나 세션이 만료될 때까지(OMV 자동 로그아웃 시간 동안 입력이 없을 때까지) 다시 묻지 않습니다. OMV 자동 로그아웃을 끄면 확인한 세션이 로그아웃할 때까지 남으므로 보안 정책 페이지가 경고를 보입니다.
- 2차 인증을 요구하는 기능이 있으면, 인증 수단을 등록한 사용자에게는 로그인 직후 2차 인증을 권합니다. 수단이 없는 기기라면 건너뛸 수 있고, 그 기능을 열 때 같은 확인 창이 나옵니다.

### 정책을 바꿀 때

- 정책을 바꾸는 관리자도 바꾸는 기능의 이전·새 단계 중 높은 쪽을 거친 세션이어야 합니다. 세션을 빼앗은 쪽이 정책을 내리고 기능을 여는 것을 막기 위해서입니다.
- 정책을 올리면 조건을 채우지 못하는 세션의 웹 터미널은 바로 닫히고 root 권한 상승도 끝납니다.
- 파일 탐색기는 다음 요청부터 막히고 창에 확인 단추가 나옵니다. "쓰기·삭제에만"이면 쓰기 작업을 할 때 확인 창이 나오고, 확인하면 그 작업을 이어서 합니다. 이미 시작한 전송은 끝까지 갑니다.

## 인증 수단 등록

각 사용자가 설정 앱의 "보안" 페이지에서 등록합니다. 등록·삭제와 복구 코드 다시 만들기는 비밀번호와(이미 등록한 수단이 있으면) 그 수단을 다시 확인한 뒤 5분 동안 할 수 있습니다. 새 기기에서 패스키를 추가할 때는 그 수단 대신 기기 추가 코드도 받습니다([새 기기에 패스키 추가](#새-기기에-패스키-추가)).

- **패스키**: 기기의 화면 잠금(지문, 얼굴, PIN)이나 보안 키로 확인합니다. 가장 권하는 방법입니다.
    - 공개 주소(`-public-origin`, [설정](configuration.ko.md))를 설정해야 하고, 브라우저가 믿는 인증서의 HTTPS 도메인으로 대시보드에 접속해야 합니다. IP 주소나 자체 서명 인증서로는 쓸 수 없고, 공개 주소를 바꾸면 패스키를 다시 등록해야 합니다.
    - 등록할 때 새 패스키로 한 번 더 확인하며, 패스키 저장소가 사용자 확인(PIN, 생체 인식)을 알려 주지 않으면 등록하지 않습니다. 잠금이 풀려 있으면 확인을 건너뛰는 비밀번호 관리자나, Windows에서 Microsoft Password Manager에만 저장되는 패스키가 그런 예입니다. 브라우저 창에서 이 기기(Windows Hello 등)나 보안 키를 골라 다시 등록해 주세요.
    - 등록하지 않은 패스키는 브라우저가 지원하면 저장소에서 지우게 하고, 지원하지 않으면 지우는 방법을 안내합니다.
    - iCloud 키체인, 비밀번호 관리자처럼 여러 기기에 동기화되는 패스키는 목록에 "동기화됨"으로 표시합니다. 막지는 않습니다.
- **인증 앱(TOTP)**: Google Authenticator, 2FAS 같은 앱의 6자리 코드입니다. QR 코드를 찍거나 키를 입력해 등록하며, 공개 주소 없이도 쓸 수 있습니다.
- **복구 코드**: 첫 수단을 등록할 때 10개를 만들어 한 번만 보여 줍니다. 코드마다 한 번씩 쓸 수 있고, 보안 페이지에서 다시 만들 수 있습니다.

## 새 기기에 패스키 추가

새 기기에는 다른 기기에서 만든 패스키가 없는 경우가 많습니다. 그래서 패스키를 추가할 때의 본인 확인은 인증 앱이 있으면 인증 앱을, 없으면 기기 추가 코드를 먼저 묻습니다. iCloud 키체인처럼 동기화되는 패스키나 휴대전화의 패스키는 "패스키 사용"을 눌러 그대로 확인할 수 있습니다.

1. 패스키가 있는 기기의 보안 페이지에서 "다른 기기에 패스키 추가"의 "코드 만들기"를 누릅니다. 그 기기에서도 비밀번호와 등록한 수단을 다시 확인합니다.
2. 새 기기의 보안 페이지에서 "패스키 추가"를 누르고, 본인 확인에서 비밀번호와 이 코드를 입력합니다.

- 코드는 10분 동안 한 번만 쓸 수 있고, 새로 만들면 이전 코드는 쓸 수 없습니다. 복구 코드와 달리 남은 복구 코드 수는 줄지 않습니다.
- 코드로 마친 본인 확인은 패스키 추가뿐 아니라 수단 삭제와 복구 코드 다시 만들기도 5분 동안 할 수 있게 합니다. 코드를 다른 사람에게 알려 주지 마세요.
- 코드로 본인 확인을 마친 세션은 2차 인증을 거친 것으로 보지 않습니다. 새 패스키를 등록하면 그때 2차 인증을 거친 세션이 됩니다.

## 복구

- 수단을 잃은 사용자는 복구 코드로 확인한 뒤 새 수단을 등록합니다.
- 복구 코드도 없으면 2차 인증을 거친 관리자가 보안 정책 페이지의 "사용자의 로그인 수단"에서 그 사용자의 수단을 초기화합니다. 그 사용자의 세션은 끝나고, 다시 로그인한 뒤 새로 등록할 수 있습니다.
- 기록 파일이 손상되어 읽을 수 없으면 그 사용자의 2차 인증을 없는 것으로 보지 않고 확인을 막습니다. 관리자가 초기화하거나 root가 아래처럼 파일을 지우면 되살아납니다.

관리자 자신의 수단을 잃었다면 root가 상태 디렉터리의 기록 파일을 지웁니다. 사용자 이름에 영문자·숫자·`_`·`-` 밖의 문자가 있으면 파일 이름에서는 `%XX`로 바뀌어 있으니 `sudo ls /var/lib/maru/security/`로 먼저 확인해 주세요.

```sh
sudo rm /var/lib/maru/security/<사용자 이름>.json
```

## 설계와 한계

- 확인은 대시보드가 하며 [권한 도우미](helper.ko.md)에는 넣지 않았습니다. 도우미의 보안 설계는 그대로입니다.
- 인증 수단 기록은 상태 디렉터리의 `security/<사용자 이름>.json`(디렉터리 `0700`, 파일 `0600`)에 있습니다. 인증 앱의 비밀 키가 들어 있으므로 상태 디렉터리를 백업할 때 함께 보호해 주세요. 복구 코드는 해시만 남깁니다. 패스키로 로그인의 키 조각도 이 기록에 있지만 혼자서는 아무것도 풀 수 없습니다([설계](passkey-login.ko.md#설계)).
- 비밀번호 재확인은 OMV에 한 번 더 로그인해서 확인하고, 틀린 횟수는 로그인 실패 횟수에 합산합니다. 2차 수단을 틀린 횟수에도 같은 기준(브라우저 IP·사용자 이름별로 15분 안에 5번째 실패부터 잠금)을 적용하지만 로그인 실패와는 따로 셉니다.
- 확인 성공·실패, 수단 등록·삭제, 패스키로 로그인 켜기·해제·로그인, 정책 변경, 초기화는 `journalctl -u maru`에 남습니다. 비밀번호·코드 같은 비밀 값은 남기지 않습니다.

막지 못하는 것도 있습니다.

- 인증 수단을 아직 등록하지 않은 계정. 첫 수단은 비밀번호만으로 등록할 수 있으므로 비밀번호가 새면 다른 사람이 먼저 등록할 수 있습니다. 2차 인증을 요구할 기능이 있다면 사용자마다 미리 수단을 등록하게 해 주세요(보안 정책 페이지의 "사용자의 로그인 수단"에서 누가 등록했는지 볼 수 있습니다).
- 대시보드(maru) 자체가 뚫린 경우. 확인 값도 대시보드를 거칩니다.
- OMV 관리자 비밀번호가 새면 OMV 웹 UI로 직접 들어가 root와 같은 일을 할 수 있습니다. 관리자 계정에는 OpenMediaVault의 2차 인증(OMV 8.5 이상)을 함께 쓰는 것을 권합니다.
- SSH 서버는 원래 LAN에 열려 있으므로, SSH에 직접 접속하는 것은 OMV의 SSH 설정이 정합니다.
