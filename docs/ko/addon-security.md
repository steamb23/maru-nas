# 애드온 보안

대시보드는 패키지 코드를 믿지 않는다는 전제로 동작합니다. 이 문서는 대시보드가 막는 것과 막지 못하는 것, 패키지 작성자가 지킬 것을 정리합니다. 관리자를 위한 설명은 [애드온 패키지](addons.md)의 "위험과 한계"에 있습니다.

## 대시보드가 막는 것

### 화면 격리

- 패키지 화면은 `sandbox="allow-scripts"` iframe에서 출처 없이 돌고, 프레임 파일의 응답에도 같은 샌드박스와 Content-Security-Policy가 붙습니다. 프레임 주소를 새 탭에서 바로 열어도 같습니다.
- 대시보드와 OMV 워크벤치의 쿠키, 브라우저 저장소, 화면(DOM), 대시보드 API에 닿지 못합니다. 프레임 파일 요청에는 쿠키 대신 세션·패키지마다 정한 토큰이 경로에 들어가고, 로그아웃하면 그 토큰은 쓸 수 없습니다.
- 직접 네트워크 요청, 다른 사이트의 스크립트·이미지, 폼 제출, 팝업, 대시보드 페이지 이동이 막힙니다. 대시보드 페이지는 같은 출처의 프레임만 띄우므로 프레임이 스스로 다른 사이트로 이동할 수도 없습니다.

### 대시보드에 보내는 요청

- 요청은 그 프레임을 띄운 패키지의 이름으로만 처리합니다. 메시지에 다른 패키지 id를 적어도 쓰이지 않습니다.
- `app.action`과 워크벤치 열기는 사용자가 그 프레임을 방금 눌렀을 때만 받습니다. `app.query`는 누르지 않아도 같은 조작을 실행하므로, 무언가를 바꾸는 조작에는 `confirm`을 붙이고 관리자만 써야 하면 `admin`도 붙이세요. 위젯은 읽기 요청만 쓸 수 있습니다.
- 요청 크기, 동시 요청 수, 빈도에 한도가 있습니다([화면 만들기](addon-frontend.md#api)).
- 대시보드가 보이는 확인 대화상자·알림·제목 표시줄에는 패키지 이름과 "애드온 패키지" 표시가 붙습니다.

### OMV 호출

- 화면은 manifest의 `rpc.read`에 밝힌 메서드만, 백엔드는 `rpc.read`와 조작을 실행하는 동안의 `rpc.write`에 밝힌 메서드만 부릅니다. 대시보드가 로그인한 사용자의 OMV 세션으로 대신 부르므로 OMV 세션 ID는 패키지에 가지 않고, 그 사용자의 OMV 권한을 넘지 못합니다.
- 내장 애드온이 쓰는 범용 RPC 중계는 패키지 메서드를 통과시키지 않습니다.
- OMV 쓰기는 백엔드가 조작을 실행하는 동안에만 부릅니다. 대시보드는 요청이 백엔드에 가기 전에 매번 조작의 관리자 전용 여부를 보고, 조작에 `confirm`이 있으면 확인 대화상자를 보입니다.
- OMV 쓰기를 선언한 패키지의 조작은 보안 정책이 꺼져 있어도 비밀번호를 다시 확인한 세션(root 권한 상승의 보안 정책이 2차 인증이면 2차 인증을 거친 세션)이어야 합니다. 세션마다 한 번 묻고, 그 확인은 세션이 끝날 때까지 남습니다. 빼앗은 세션 쿠키만으로는 패키지가 OMV에 쓰게 할 수 없습니다.

### 백엔드

- 대시보드는 패키지의 실행 파일을 스스로 실행하지 않습니다. 지금 버전에서 백엔드는 개발 서버에서만 돌고, 설치본의 백엔드는 이후 버전에서 따로 샌드박스에서 돌게 됩니다([애드온 백엔드](addon-backend.md#설치본의-백엔드)).
- 백엔드는 OMV 세션 ID, 비밀번호, 대시보드 쿠키, root를 받지 않습니다. 요청마다 만든 호출 토큰으로 대시보드의 호스트 소켓을 거쳐 OMV를 부릅니다. 토큰은 그 요청이 끝날 때까지, 그 패키지의 호스트 소켓에서만 쓸 수 있으므로 백엔드가 스스로, 또는 다른 패키지의 권한으로 OMV를 부를 수 없습니다.
- 호스트 소켓은 선언한 메서드만(데이터 요청에서는 읽기만) 부르고, 허용하지 않는 메서드 표를 한 번 더 봅니다. OMV에 적용 대기가 있으면 설정 적용을 거절하므로, 다른 사람이 만든 변경을 패키지가 대신 배포하지 않습니다.
- 백엔드의 응답은 정한 상태의 JSON만 통과합니다. 오류 코드는 형식을 검사하고, 문구는 제어 문자와 양방향 제어 문자를 지우고 300자로 자르며, 응답 헤더는 버립니다. 백엔드는 사용자를 로그아웃시키거나 대시보드의 오류 코드를 흉내 낼 수 없고, 그 문구는 대시보드의 대화상자나 알림이 아니라 자기 프레임 안에만 보입니다.
- 조작은 모두 사용자, 패키지, 조작, 대상, 결과와 함께 서버 로그에 남습니다.

### 허용하지 않는 메서드

호출한 쪽이 명령·스크립트·패키지·파일 내용·호스트 경로를 정하는 메서드, 자격 증명을 돌려주거나 비밀번호를 확인하는 메서드, 대시보드가 맡는 흐름은 선언할 수 없습니다. 선언하면 설치하지 않습니다("허용 안 됨"). 서비스 이름은 대소문자를 가리지 않습니다.

| 대상 | 이유 |
|---|---|
| `Session`, `Exec`, `Config` 서비스 전체 | 로그인·백그라운드 작업·설정 적용은 대시보드가 맡습니다 |
| `Cron`, `Scripts`, `PluginMgmt`, `Apttool`, `Omvextras`, `EnvVars` 서비스 전체 | 명령·스크립트 실행, 패키지·저장소 설치, 환경 변수 |
| `Apt.install`, `upgrade`, `update`, `upload`, `getChangeLog` | 패키지 설치, 셸 명령에 들어가는 인자 |
| `Compose`의 명령·로그·파일 메서드(`doCommand`, `doCommandList`, `doPrune`, `doServiceCommand`, `doContainerCommand`, `getContainerLog`, `doAutocompose`, `doDockerCmd`, `doDockerVolumeCmd`, `doDockerNetworkCmd`, `doDockerImageCmd`, `doNetworkConnect`, `doGit`, `doBuild`, `doJob`, `setJob`, `setFile`, `setDockerfile`, `setConfig`, `setGlobalEnv`, `doRestore`) | Docker·compose 명령을 만들거나 파일을 씁니다 |
| `UserMgmt`의 `set*`, `delete*`, `import*`, `authUser` | 사용자·그룹 변경(sudo 그룹에 넣기 등), 비밀번호 확인 |
| `EmailNotification.get`, `Rsync.get`, `Network.getProxy`, `Network.getInterface`, `Network.getInterfaceList`, `Network.getWirelessIface` | 비밀번호·무선 키를 돌려줍니다 |
| `Symlinks.setSymlink`, `Kvm.setVmXml`, `Kvm.addFsPass`, `Kvm.addHostDisk` | 호스트 경로·장치를 엽니다 |

이 표는 직접적인 경로만 막습니다. 표에 없는 OMV 쓰기(서비스 설정의 추가 옵션 등)로도 root에 이를 수 있으므로, OMV 쓰기를 선언한 패키지는 검토 화면에 위험으로 표시합니다. 표를 줄이자는 제안은 이슈에서 먼저 논의해 주세요.

### 설치와 저장

- OMV 관리자만 설치하고, 설치·업데이트·다시 켜기는 비밀번호(보안 수단을 등록했으면 그 수단도)로 다시 확인합니다. OMV 쓰기, 백엔드, 네트워크가 있는 패키지는 쓰기 조작에 필요한 확인도 거칩니다.
- 패키지 파일은 경로·형식·크기를 검사하고 따로 풀어 둔 뒤 옮깁니다. 받은 파일 권한은 쓰지 않습니다.
- 패키지의 사용자별 저장값은 패키지와 사용자마다 따로 둡니다. 지웠다가 다시 설치한 패키지(같은 id의 다른 작성자일 수 있습니다)는 이전 값을 읽지 못합니다.

## 대시보드가 막지 못하는 것

- 화면에 보인 값의 유출: WebRTC와 DNS 미리 가져오기는 Content-Security-Policy로 완전히 막지 못합니다. 패키지 화면이 받은 값은 작성자에게도 갈 수 있다고 보세요.
- 가짜 입력 화면: 패키지 창 안에 그린 비밀번호 입력 칸을 대시보드가 구별할 수 없습니다. 대시보드는 패키지 창 안에서 비밀번호를 묻지 않는다고 사용자에게 알립니다.
- 선언한 메서드가 주는 값: `System.getInformation`을 선언하면 그 결과 전체를 읽습니다. 관리자가 열면 관리자에게만 오는 값도 읽습니다.
- 작성자 확인: 서명이 없습니다. 관리자는 받은 곳과 SHA-256으로 확인합니다.
- 함께 쓰는 백엔드: 모든 사용자가 백엔드 하나를 씁니다. 백엔드는 관리자 세션으로 읽은 값을 일반 사용자에게 보여 줄 수 있고, 백엔드가 두는 데이터는 모두가 함께 씁니다. 패키지를 쓰는 모든 사용자에 대해 선언한 메서드의 결과도 봅니다.
- 설치본 백엔드(이후 버전)의 네트워크. manifest의 `backend.network`가 허용한 대로입니다.
    - `lan`은 LAN의 기기에 닿고, LAN의 DNS 리졸버와 프록시를 거쳐 인터넷에도 닿을 수 있습니다. 이 서버의 Docker 네트워크도 보통 같은 사설 주소 범위(172.16.0.0/12)를 쓰므로 그 컨테이너에도 닿습니다.
    - `loopback`은 이 서버에서 루프백으로 받는 모든 서비스에 닿습니다. OMV 웹 서버, sshd, 대시보드 자신의 수신 주소(백엔드가 비밀번호를 대입해 볼 수 있습니다), 로컬 DNS 리졸버가 그렇습니다.
    - 어느 쪽이든 네트워크를 허용하면 백엔드가 서버의 네트워크 이름공간을 함께 쓰므로, 그 안의 추상 유닉스 소켓(컨테이너 도구의 소켓 등)에도 닿습니다.

## 작성자가 지킬 것

- 필요한 메서드만 선언하고, README에 각 메서드를 왜 쓰는지 적어 주세요.
- 관리자에게만 오는 값은 `context.admin`을 보고 다룹니다. 일반 사용자 화면에 관리자 값을 남기지 마세요.
- 비밀번호, 토큰, OMV 계정 정보를 화면에서 묻거나 저장값에 두지 마세요.
- OMV가 돌려준 문자열(호스트 이름, 공유 폴더 이름 등)과 사용자 입력은 `textContent`로 넣고 `innerHTML`에 넣지 마세요. 프레임 안에서도 다른 사용자의 화면을 망가뜨릴 수 있습니다.
- 백엔드에서는 요청마다 사용자와 관리자 여부를 보고 돌려줄 값을 정하세요. 관리자 세션으로 읽은 값을 두었다가 일반 사용자에게 돌려주지 말고, 사용자의 비밀을 데이터 디렉터리에 두지 마세요.
- 조작의 `target`과 `input`은 OMV 파라미터에 넣기 전에 백엔드에서 검사하세요. OMV 설정을 바꾸는 조작은 `confirm`이 있는 관리자 전용으로 두고 `Host.Apply`로 적용하세요.
- 백엔드에 필요하지 않으면 네트워크를 요청하지 말고, `lan`·`loopback`을 요청한다면 README에 이유를 적어 주세요. 호출 토큰은 로그에 남기지 마세요.
- 외부 서비스에 닿는 기능은 만들지 마세요. 화면은 네트워크에 닿지 못하고, 백엔드에는 인터넷을 허용하는 값이 없으며, 마루 NAS는 로컬 네트워크 전용입니다.
