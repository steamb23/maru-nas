# <img src="frontend/src/assets/logo/onmaru-lockup.svg" alt="온마루 (Onmaru)" height="80">

> A suspiciously normal desktop-like dashboard for openmediavault.

OpenMediaVault 8 위에 올리는 데스크톱형 웹 대시보드입니다. 창·작업표시줄·바탕화면 위젯으로 NAS 가동 현황을 확인하고, 컨테이너와 핵심 서비스를 간단히 켜고 끌 수 있습니다. 심층 설정은 OMV 기본 웹 UI에서 합니다.

- 로컬 네트워크 전용입니다. 인터넷에 노출하는 구성을 전제로 하지 않으며, 인터넷에 노출되었을 때 어떤 보안 취약점이 드러날지 충분히 검증되지 않았습니다.
- 로그인은 OMV 계정으로 합니다. 백엔드가 OMV `rpc.php`에 로그인을 위임하며, 설정 변경도 로그인한 사용자의 OMV 세션으로만 합니다.
- Go 실행 파일 하나(프론트엔드 포함)를 systemd 서비스로 실행하고, 앞단의 리버스 프록시가 HTTPS를 맡습니다.

## 빌드 및 설치

### 준비

OpenMediaVault 8의 모든 버전(8.0 이상)에서 동작합니다. 버전에 따라 다음이 다릅니다.

- 2단계 인증은 OMV 8.5 이상에서만 쓸 수 있습니다. OMV 8.5에서 생긴 기능이기 때문입니다.
- OMV 8.0·8.1은 자동 로그아웃 시간을 알려 주지 않습니다. 그래서 대시보드에 세션의 남은 시간이 표시되지 않고, OMV 세션이 끝난 것은 대시보드가 주기적으로 OMV에 확인할 때 알게 됩니다.

OMV 설치 이미지(ISO)로 막 설치했다면 이미지의 버전이 그대로 설치됩니다(예: 8.3.1 이미지는 OMV 8.3.1). 보안 업데이트도 받을 수 있게 OMV 웹 UI의 시스템 → 업데이트 관리에서 업데이트하거나 `sudo omv-upgrade`를 실행해 두기를 권장합니다. 지금 버전은 `dpkg-query -W openmediavault`로 확인합니다.

빌드에는 아래 도구가 필요합니다. OMV 설치 이미지로 설치한 직후에는 어느 것도 들어 있지 않지만, 모두 OMV 8(Debian 13)이 기본으로 쓰는 apt 저장소에서 설치할 수 있습니다.

| 도구 | 필요한 버전 | apt 패키지(버전) | 비고 |
|---|---|---|---|
| Go | 1.27.1 이상 | `golang-go`(trixie-backports 1.27, 기본 저장소 1.24) | `backend/go.mod` 기준입니다. |
| Node.js | 20.19 이상 또는 22.12 이상 | `nodejs`(20.19) | Vite 8 기준입니다. |
| npm | 7 이상 | `npm`(9.2) | Debian에서는 `nodejs`와 따로 설치합니다. |
| make | GNU make | `make`(4.4) | |
| git | | `git`(2.47) | 소스와 아이콘 서브모듈을 받고, 빌드할 때 커밋 정보를 실행 파일에 넣습니다. |

```sh
sudo apt install git make nodejs npm
sudo apt install -t trixie-backports golang-go
```

- OMV는 커널 업데이트용으로 Debian의 trixie-backports 저장소를 기본으로 켜 둡니다. 두 번째 줄은 그 저장소에서 Go 1.27을 설치합니다.
- `-t trixie-backports` 없이 설치하면 Go 1.24가 설치됩니다. 이때는 첫 빌드에서 Go가 1.27.1 툴체인을 proxy.golang.org에서 자동으로 내려받습니다(약 75MB). 내려받은 파일과 푼 툴체인을 합쳐 `~/go/pkg/mod`에 약 330MB가 생깁니다. `GOTOOLCHAIN=local`로 설정했거나 proxy.golang.org에 접속할 수 없다면 backports나 [go.dev/dl](https://go.dev/dl/)의 배포본을 설치해 주세요.
- C 컴파일러와 `curl`은 필요하지 않습니다. 설치 끝의 상태 확인은 설치기가 직접 합니다.
- Node.js 20에서는 `npm ci`가 Vitest의 `EBADENGINE` 경고를 표시합니다. 개발용 테스트 도구에 대한 경고이므로 빌드에는 영향이 없습니다.
- root 계정이라면 `sudo` 없이 실행합니다.
- 빌드하는 동안 github.com(아이콘 서브모듈), registry.npmjs.org(npm 의존성), proxy.golang.org(Go 의존성)에 접속하며, 도구 설치와 빌드에 약 1.1GB의 여유 공간이 필요합니다(backports의 Go 기준. 기본 저장소의 Go 1.24를 쓰면 툴체인 때문에 약 0.3GB가 더 필요합니다).

소스는 git으로 받습니다. `stable` 브랜치가 최신 릴리스이고 `main`은 개발 중인 코드이므로 설치에는 `stable`을 받습니다. 아이콘 서브모듈은 설치 스크립트가 받으므로 `--recurse-submodules`는 필요 없습니다.

```sh
git clone -b stable https://github.com/steamb23/Onmaru.git
cd Onmaru
```

특정 버전을 설치하려면 클론한 뒤 그 버전의 태그를 체크아웃합니다(예: `git checkout v0.10.0`). 릴리스 목록과 변경 내용은 [Releases](https://github.com/steamb23/Onmaru/releases)에 있습니다.

### 설치 스크립트

```sh
./install.sh
```

일반 사용자 계정이라면 **sudo 없이** 실행해 주세요. `install.sh`는 Go로 만든 설치기(`installer/`)를 실행한 계정으로 빌드해(`bin/onmaru-install`) 실행하며, 설치는 다음 순서로 진행됩니다.

1. **설정 입력**: 서비스 사용자, 수신 방식, OMV 주소, SMART 갱신 시각, OMV 워크벤치 주소, 패스키에 쓸 공개 주소, 권한 도우미 설치 여부, 대시보드에서 업그레이드 허용 여부를 묻고 요약을 보여 준 뒤 확인을 받습니다. 입력은 이 단계에서 모두 끝납니다. 이미 설치되어 있으면 묻지 않고 설치된 설정으로 업그레이드합니다(아래 "업그레이드" 참고).
2. **빌드**: 실행한 계정으로 빌드합니다. 처음 클론한 상태라면 아이콘 서브모듈과 npm 의존성부터 준비합니다(`make build` → `bin/onmaru`, `bin/onmaru-helper`, `bin/onmaru-install`).
3. **설치**: root 권한이 필요한 단계입니다. 일반 사용자라면 설치기가 1단계의 설정을 옵션으로 넘겨 스스로 `sudo bin/onmaru-install --service-install ...`을 실행하므로 비밀번호만 한 번 입력하면 됩니다. root 계정만 있는 환경이라면 sudo 없이 그대로 이어서 진행합니다.

터미널에서 실행하면 화살표 키로 고르고 값을 입력하는 화면(TUI)으로 묻고, 잘못된 값은 입력하는 동안 바로 알려 줍니다. `--plain`을 주거나 `TERM=dumb`이면 한 줄씩 묻습니다. 표준 입력이 터미널이 아니면(파이프, 자동화 등) 묻지 않고, 빠진 설정 옵션의 목록을 알린 뒤 멈춥니다.

OMV 설치 이미지가 만든 일반 사용자는 sudo 그룹에 들어 있으므로 이 방식으로 설치할 수 있습니다. 다만 OMV는 root와 `_ssh` 그룹 사용자에게만 SSH 접속을 허용하므로, 그 계정으로 SSH에 접속하려면 OMV 웹 UI의 사용자 편집 화면에서 `_ssh` 그룹을 더해 주세요.

설치 단계에서는 다음 작업을 합니다.

- 시스템 사용자를 만들고(기본값 `onmaru`), `bin/onmaru`를 `/usr/local/bin/onmaru`에 설치합니다.
- 설정 파일 `/etc/default/onmaru`와 systemd 유닛 `/etc/systemd/system/onmaru.service`를 작성한 뒤 서비스를 시작합니다.
- 사용자 설정(위젯 배치, 바탕화면 바로가기, 화면 설정 등), 관리자의 전역 설정, 올린 배경 이미지는 `/var/lib/onmaru`(`StateDirectory=`)에 저장됩니다.
- 권한 도우미(기본값 설치)는 `/usr/local/bin/onmaru-helper`, `/etc/default/onmaru-helper`, `/etc/systemd/system/onmaru-helper.socket`·`.service`를 작성하고 소켓을 켭니다. 설치하지 않기로 하면 이전에 설치한 도우미를 지웁니다(아래 "권한 도우미" 참고).
- 대시보드에서 업그레이드를 허용하면(권한 도우미를 설치할 때의 기본값) 업그레이드 서비스 `/etc/systemd/system/onmaru-upgrade.service`·`.path`, root 소유 설치기 복사본 `/usr/local/lib/onmaru/onmaru-install`, 설정 파일 `/etc/default/onmaru-upgrade`를 작성하고 경로 유닛을 켭니다. 허용하지 않으면 이전에 설치한 것을 지웁니다(아래 "대시보드에서 업그레이드" 참고).
- 설치한 버전과 커밋을 `/var/lib/onmaru-upgrade/installed.json`에 기록합니다. 커밋은 설치한 `bin/onmaru`에서 읽으며, `--no-build`로 설치기와 다른 커밋에서 빌드한 `bin/onmaru`를 설치하는 경우처럼 버전을 확인할 수 없으면 버전을 비워 두고 경고합니다.

이미 설치된 상태에서 다시 실행하면 설치된 설정으로 업그레이드합니다(아래 "업그레이드" 참고). 설정을 바꾸려면 `./install.sh --reinstall`을 실행합니다. 지금 설정을 기본값으로 보여 주며 모든 설정을 다시 묻습니다. 설정이 바뀌면 기존 `/etc/default/onmaru`는 `/etc/default/onmaru.bak-<시각>`으로 백업됩니다. 설치기가 묻지 않는 줄은 그대로 남습니다. 웹 터미널 줄(`ONMARU_TERMINAL` 등)은 기존 값을 옮기고, 손으로 넣은 다른 `ONMARU_*` 줄(예: `ONMARU_COOKIE_PATH`)은 파일 끝의 "Kept from the previous file" 주석 아래로 옮깁니다. 안내 문구는 로캘에 따라 영어 또는 한국어로 표시되며, `--lang en|ko`로 직접 고를 수도 있습니다.

| 옵션 | 설명 |
|---|---|
| (없음) | 설정을 묻고 빌드한 뒤 설치합니다. 이미 설치되어 있으면 설치된 설정으로 업그레이드합니다. 기존 설치에 없는 설정만 묻고, 요약 뒤에 업그레이드·설정 바꾸기·취소 중에서 고릅니다(표준 입력이 터미널이 아니면 묻지 않고 업그레이드합니다). |
| `--reinstall` | 설치된 값을 기본값으로 모든 설정을 다시 묻고 다시 설치합니다. 설치되어 있지 않으면 처음 설치와 같습니다. |
| `--upgrade` | 스크립트용입니다. 설치된 설정으로 확인 없이 업그레이드하며, 설치되어 있지 않으면 실패합니다. 기존 설치에 없는 설정(새 버전에서 생긴 설정)만 묻습니다. |
| `--no-build` | 빌드를 건너뛰고 기존 `bin/onmaru`(권한 도우미를 설치하면 `bin/onmaru-helper`도)를 설치합니다. |
| `--uninstall` | 서비스, 실행 파일, 설정을 제거합니다. |
| `--service-install` | 빌드 없이 설치 단계만 실행합니다(root 전용). 아래 설정 옵션을 모두 주면 묻지 않고 설치합니다. |
| `--dry-run` | 설치 단계를 실행하지 않고, 쓸 파일의 바뀌는 내용과 실행할 명령만 보여 줍니다. sudo를 쓰지 않고 시스템을 바꾸지 않습니다. `--no-build`가 없으면 빌드는 실제로 합니다(저장소 안에만 씁니다). |
| `--upgrade-plan` | 기존 설치를 읽기만 하고, 이 버전으로 업그레이드할 때 물어야 할 설정과 수동 재설치가 필요한 이유를 JSON으로 출력합니다. 대시보드에서 업그레이드하는 기능을 위한 옵션이며 시스템을 바꾸지 않습니다. |
| `--upgrade-service` | 대시보드에서 업그레이드의 확인·적용 요청 하나를 처리합니다(root 전용). 업그레이드 서비스(`onmaru-upgrade.service`)가 root 소유 설치기 복사본으로 실행하므로 직접 실행하지 않습니다. |
| `--plain` | TUI 대신 한 줄씩 묻습니다. |
| `--lang en\|ko` | 안내 문구 언어를 고릅니다. |
| `-h`, `--help` | 사용법을 보여 줍니다. |
| `--user NAME` | 서비스 사용자입니다(기본값 `onmaru`). |
| `--listen ADDR` | 수신 주소입니다. `127.0.0.1:8090`, `unix:/run/onmaru/onmaru.sock`, 또는 `host:port`를 지정합니다. |
| `--allow-non-loopback` | 루프백이 아닌 `--listen` 주소를 허용합니다(위험). |
| `--omv-url URL` | OMV 웹 UI 주소입니다(루프백). |
| `--smart-refresh-at HH:MM` | SMART 정보를 매일 다시 가져올 시각입니다. |
| `--workbench-url URL` | 브라우저에서 OMV 웹 UI를 열 주소입니다. 빈 값(`--workbench-url ''`)이면 "OMV 워크벤치" 앱을 숨깁니다. 질문에서는 `-`를 입력하면 끕니다. |
| `--public-origin URL` | 브라우저가 대시보드에 접속하는 공개 HTTPS 주소입니다(보안 강화 모드의 패스키용). 빈 값(`--public-origin ''`)이면 패스키를 끕니다. 질문에서는 `-`를 입력하면 끕니다. |
| `--helper`, `--no-helper` | 권한 도우미(root로 도는 `onmaru-helper`)를 설치하거나 설치하지 않습니다. 질문의 기본값은 설치입니다. `--no-helper`는 이미 설치된 도우미를 지웁니다. |
| `--elevate-group GROUP` | root 권한 상승에 `openmediavault-admin`과 함께 필요한 그룹입니다(기본값 `sudo`). `--helper`일 때만 씁니다. |
| `--web-upgrade`, `--no-web-upgrade` | 대시보드에서 업그레이드하는 것을 허용하거나 허용하지 않습니다. `--helper`일 때만 쓰며, 저장소 소유자가 root이면 허용할 수 없습니다. 새로 설치할 때 질문의 기본값은 허용이고, 이 설정이 없던 버전에서 업그레이드하면 허용하지 않은 것으로 보고 묻지 않습니다. 아래 "대시보드에서 업그레이드"를 참고해 주세요. |
| `--build-path PATH` | 대시보드에서 업그레이드할 때 저장소 소유자 계정으로 git과 빌드를 실행할 PATH입니다. 묻지 않습니다. 일반 사용자로 `./install.sh`를 실행하면 그때 git·go·node·npm·make를 찾은 디렉터리로 정하고, 대시보드에서 업그레이드하거나 root로 `--service-install`을 실행하면 기존 값을 씁니다. |

설정 옵션으로 준 항목은 묻지 않습니다. 처음 설치나 `--reinstall`은 설정을 모두 주더라도 요약을 보여 주고 진행 여부를 확인하므로, 표준 입력이 터미널이 아니면 이 확인에서 멈춥니다. 확인을 생략하는 것은 업그레이드(옵션 없이 실행한 비TTY, `--upgrade`)와 root로 `--service-install`에 설정을 모두 준 경우이므로, 처음 설치를 자동화할 때는 다음과 같이 사용합니다(빌드는 미리 해 두어야 합니다). 무엇이 바뀌는지는 같은 옵션에 `--dry-run`을 더해 먼저 볼 수 있습니다.

```sh
./install.sh --service-install --user onmaru --listen unix:/run/onmaru/onmaru.sock \
  --omv-url http://127.0.0.1 --smart-refresh-at 00:00 --workbench-url https://nas.example.lan/ \
  --public-origin '' --no-helper
```

root로 실행했는데 저장소의 소유자가 root가 아니면(`sudo ./install.sh`, `sudo -i`, `su` 등) 빌드를 건너뜁니다. root로 빌드하면 저장소에 root 소유 파일이 생기고, sudo 환경의 PATH에는 사용자가 설치한 Go·npm이 없을 수 있기 때문입니다. 이때 설치기도 빌드하지 않고 이미 있는 `bin/onmaru-install`을 쓰며, 기존 `bin/onmaru`로 설치만 할지 물어봅니다(`--upgrade`이거나 표준 입력이 터미널이 아닌 업그레이드면 묻지 않고 멈춥니다). PATH에 `go`가 없을 때도 이미 있는 `bin/onmaru-install`을 씁니다.

### 업그레이드

```sh
git pull
./install.sh
```

`stable`을 받았다면 `git pull`로 최신 릴리스가 내려옵니다. 태그를 체크아웃해 특정 버전을 쓰고 있다면 `git pull` 대신 `git fetch --tags`로 받고 새 버전의 태그를 체크아웃합니다.

이미 설치되어 있으면(`/etc/systemd/system/onmaru.service`와 `/etc/default/onmaru`가 모두 있으면) `./install.sh`는 지금 설치된 설정(유닛의 서비스 사용자, `/etc/default/onmaru`의 나머지 설정)을 그대로 써서 빌드하고 설치합니다. 설정 질문과 포트 사용 중·OMV의 Force SSL/TLS 같은 경고의 확인을 건너뛰고(경고는 표시합니다), 요약을 보여 준 뒤 "업그레이드", "설정 바꾸기", "취소" 중에서 고르게 합니다. "설정 바꾸기"는 지금 값을 기본값으로 모든 설정을 다시 묻습니다(`--reinstall`과 같습니다). 표준 입력이 터미널이 아니면 고르지 않고 업그레이드합니다. 일반 사용자라면 sudo 비밀번호만 입력하면 됩니다.

스크립트에서는 `./install.sh --upgrade`를 씁니다. 확인 없이 업그레이드하고, 설치되어 있지 않으면 설치하지 않고 실패합니다. 둘 중 한 파일만 있는 상태(일부만 설치된 상태)에서 옵션 없이 실행하면 경고하고 `--reinstall`처럼 모든 설정을 묻습니다.

- 새 버전에서 설정이 추가되어 기존 설치에 그 값이 없으면 그 설정만 묻습니다.
- 설정 옵션(`--listen` 등)을 함께 주면 그 항목만 기존 값 대신 씁니다.
- 수신 주소와 서비스 사용자가 그대로면 리버스 프록시 설정도 그대로 맞으므로, 끝난 뒤 리버스 프록시 안내 없이 로그 위치만 알립니다.
- 보안 강화 모드가 생기기 전 버전에서 올라오면 패스키에 쓸 공개 주소(`--public-origin`)를 묻습니다. `-`를 입력하면 패스키를 끄고 넘어갑니다.
- 권한 도우미가 생기기 전 버전에서 올라오면 도우미 설치 여부를 묻습니다. 설치되어 있다면 도우미도 새 실행 파일로 다시 시작합니다(대시보드도 다시 시작하므로 어차피 모두 다시 로그인합니다).
- 기존 설치의 값이 새 버전의 검사를 통과하지 못하면 경고하고 그 설정만 다시 묻습니다(기존 값이 아닌 기본값을 보여 줍니다).
- 표준 입력이 터미널이 아니어도 동작합니다. 기존 설치에 없는 설정이나 검사를 통과하지 못한 설정이 있으면 그 옵션 목록을 알리고 멈추므로, 옵션으로 주거나 `--reinstall`로 다시 실행합니다.

### 대시보드에서 업그레이드

SSH로 `git pull`과 `./install.sh`를 실행하는 대신, 관리자가 대시보드에서 온마루를 업그레이드할 수 있습니다. 설치에 쓴 로컬 git 저장소에서 새 버전을 찾고, 저장소 소유자 계정으로 빌드한 뒤 root로 설치합니다. 설정 앱의 "업데이트" 페이지(관리자)에서 합니다.

- **켜기**: 권한 도우미를 설치할 때 `--web-upgrade`(질문의 기본값)로 허용하고 `--no-web-upgrade`로 끕니다. 이 설정이 없던 버전에서 업그레이드하면 꺼진 채로 두므로, 켜려면 `./install.sh --web-upgrade`나 `./install.sh --reinstall`을 실행합니다.
- **조건**: 저장소를 일반 사용자 계정으로 클론해야 합니다. 저장소 소유자가 root이면 허용할 수 없습니다. git과 빌드는 저장소 소유자 계정으로 실행하며, 그 계정에서 git·Go·Node.js·npm·make를 쓸 수 있어야 합니다. 설치 스크립트는 일반 사용자로 실행할 때마다 이 도구를 찾은 디렉터리를 빌드 PATH(`--build-path`)로 기록하므로, 도구를 옮겼다면 저장소 소유자 계정으로 `./install.sh`를 다시 실행합니다.
- **구성**: 경로 유닛 `onmaru-upgrade.path`가 확인·업그레이드 요청을 지켜보다가 `onmaru-upgrade.service`를 실행합니다. 이 서비스는 저장소 안의 실행 파일이 아니라 설치할 때 root 소유로 복사해 둔 설치기(`/usr/local/lib/onmaru/onmaru-install --upgrade-service`)로 돌고, 진행과 결과를 `/var/lib/onmaru-upgrade/status.json`에 씁니다. 로그는 `journalctl -u onmaru-upgrade`에 있습니다.
- **순서**: 업데이트 페이지에서 확인을 누르면 새 버전, 그 사이의 커밋 목록, 새 버전이 묻는 설정, 업그레이드한 뒤 할 일을 보여 줍니다. 웹으로 할 수 없는 업그레이드면 그 대신 이유와 SSH로 실행할 명령을 보여 줍니다. 물은 설정에 답하고 "업그레이드"를 누르면 비밀번호로 root 권한 상승을 한 뒤 진행 단계를 보여 주고, 설치 단계에서 "온마루를 다시 시작하는 중" 화면으로 바뀝니다. 온마루가 돌아오면 페이지를 새로 고치고, 다시 로그인하면 업데이트 페이지가 결과를 보여 줍니다. 빌드가 오래 걸려 그동안 대시보드를 조작하지 않으면 OMV 세션이 끝나 로그인 화면으로 먼저 돌아갈 수 있습니다. 업그레이드는 그대로 진행되며, 다시 로그인하면 업데이트 페이지가 진행 상황을 이어서 보여 줍니다.
- **확인**: "원격에서 가져와 확인"은 저장소 소유자 계정으로 `git fetch`를 하고 지금 브랜치의 추적 브랜치(예: `origin/stable`)를 대상으로 삼습니다. 지금 체크아웃에서 그 브랜치로 fast-forward할 수 있어야 합니다. "로컬 저장소만 확인"은 SSH로 받아 둔 지금 체크아웃(HEAD)을 대상으로 삼으므로 태그를 체크아웃한 설치나 로컬 커밋도 쓸 수 있습니다. 두 방식 모두 작업 트리에 커밋하지 않은 변경이 없어야 하고, 대상이 설치된 커밋에서 이어져야 합니다. 확인은 대상 커밋의 설치기만 저장소 소유자 계정으로 임시 빌드해 새 버전이 묻는 설정과 수동 재설치가 필요한지 알아내며, 저장소 코드를 root로 실행하지 않습니다. 같은 방식으로 확인에 성공한 지 30초가 지나지 않았다면, 다시 눌러도 새로 확인하지 않고 그 결과를 그대로 보여 줍니다.
- **업그레이드**: root 권한 상승(비밀번호 재입력)이 필요합니다. 서비스는 확인 결과와 저장소 상태를 다시 확인하고, 입력한 설정 값을 새 버전의 검사로 확인한 뒤, fast-forward(원격에서 가져온 경우), 저장소 소유자 계정으로 빌드, 새 설치기로 설치(`--service-install --upgrade`) 순서로 진행합니다. 설치하면 onmaru와 권한 도우미가 다시 시작하므로 모든 사용자가 다시 로그인합니다.
- **원격 가져오기의 자격 증명**: 저장소 소유자 계정의 git 설정과 자격 증명을 그대로 쓰며 비밀번호나 SSH 호스트 키 확인을 묻지 않습니다(`GIT_TERMINAL_PROMPT=0`, SSH `BatchMode`). 그 계정에서 묻는 것 없이 `git fetch`가 되어야 합니다.
- **수동 재설치 안내**: 웹으로 넘을 수 없는 변경이면(설치 기록이 없음, 로컬 커밋으로 fast-forward할 수 없음, 새 버전이 웹에서 물을 수 없는 설정을 추가함, 필요한 Go·Node.js 버전이 더 높음 등) 업그레이드 대신 이유와 명령을 보여 줍니다. 저장소 소유자 계정으로 SSH 접속해 저장소에서 `./install.sh`(또는 `./install.sh --reinstall`)를 실행합니다. 한 번 수동으로 올리면 그다음 버전부터 다시 대시보드에서 업그레이드할 수 있습니다.
- **실패했을 때**: 빌드 전이나 빌드 중에 실패하면 설치된 것은 바뀌지 않습니다. 다만 원격에서 가져와 진행했다면 작업 트리는 fast-forward된 채로 남을 수 있습니다. 설치 단계에서 실패하면 대시보드가 뜨지 않을 수 있으므로 SSH로 저장소에서 `./install.sh`를 다시 실행해 복구합니다. 자동으로 이전 버전으로 되돌리지 않습니다.
- **상태 디렉터리**: 업그레이드 서비스는 `/var/lib/onmaru` 안의 확인 요청만 지켜보므로, `ONMARU_STATE_DIR`로 상태 디렉터리를 옮긴 설치에서는 업데이트 페이지가 꺼져 있습니다.
- **제한**: 같은 때에 SSH로 `./install.sh`를 실행하는 것을 막지 않으므로, 대시보드에서 업그레이드하는 동안에는 수동 설치를 하지 마세요. 아이콘 서브모듈은 fast-forward한 뒤 `git submodule update --init --depth 1`로 맞추므로, 서브모듈 커밋이 바뀐 버전은 서브모듈 원격(GitHub)에서 그 커밋을 받을 수 있어야 합니다.

개발 서버(`make dev`)의 백엔드도 기본으로 `127.0.0.1:8090`을 사용합니다. 같은 머신에서 개발한다면 서비스는 Unix 소켓이나 다른 포트로 설치해 주세요. 설치 스크립트는 포트가 이미 사용 중이면 경고합니다.

제거하려면 `./install.sh --uninstall`을 실행합니다. 권한 도우미와 대시보드 업그레이드 서비스를 설치했다면 함께 지우고, 설치 기록과 업그레이드 상태(`/var/lib/onmaru-upgrade`)도 지웁니다. `/var/lib/onmaru`와 서비스 사용자는 확인을 받은 뒤에만 삭제합니다. 제거하면 `/run/onmaru`도 지워지므로, 컨테이너 프록시에 이 디렉터리를 마운트해 두었다면 다시 설치한 뒤 프록시 컨테이너를 다시 만들어야 합니다.

리버스 프록시는 설치 스크립트가 설정하지 않습니다. 아래 "리버스 프록시" 항목을 참고해 주세요.

## 설정

`/etc/default/onmaru`의 환경 변수나 명령줄 플래그로 설정합니다. 값을 바꾼 뒤에는 `sudo systemctl restart onmaru`로 다시 시작해 주세요. 지금 쓰는 값과 그 출처(기본값, 환경 변수, 명령줄 플래그)는 관리자가 설정 앱의 "서버" 페이지에서 볼 수 있습니다.

워크벤치 주소(`-workbench-url`), SMART 확인 시각(`-smart-refresh-at`), 웹 터미널 허용(`-terminal`)은 설정 앱의 "서버" 페이지에서 바꿀 수도 있습니다. 여기서 바꾼 값은 상태 디렉터리의 `site.json`에 저장되어 플래그·환경 변수보다 우선하며, 다시 시작하지 않아도 바로 적용됩니다. `install.sh`로 다시 설치하거나 업그레이드해도 그대로 남으므로, 플래그 값으로 돌아가려면 그 페이지에서 "서버 값 사용"을 눌러 주세요.

| 플래그 | 환경 변수 | 기본값 | 설명 |
|---|---|---|---|
| `-listen` | `ONMARU_LISTEN` | `127.0.0.1:8090` | 수신 주소입니다. 루프백 `host:port` 또는 `unix:/절대/경로.sock`(Unix 소켓, 권한 `0660`)을 지정합니다. |
| `-allow-non-loopback` | `ONMARU_ALLOW_NON_LOOPBACK` | `false` | 루프백이 아닌 TCP 주소(`0.0.0.0:8090` 등)도 허용합니다. 위험하니 아래 설명을 먼저 읽어 주세요. |
| `-omv-url` | `ONMARU_OMV_URL` | `http://127.0.0.1` | OMV 웹 UI(nginx) 주소입니다. 백엔드가 `<주소>/rpc.php`로 로그인을 위임합니다. 루프백 주소만 허용합니다. OMV 웹 UI 포트를 바꿨다면 포트까지 적어 주세요(설치 스크립트는 nginx 설정에서 포트를 찾아 제안합니다). 백엔드는 평문 HTTP로만 접속하므로 OMV의 "Force SSL/TLS"는 꺼져 있어야 합니다. |
| `-cookie-path` | `ONMARU_COOKIE_PATH` | `/` | 브라우저가 보는 대시보드 경로(세션 쿠키의 Path)입니다. 경로 접두사 아래에 둘 때 좁힐 수 있습니다. |
| `-state-dir` | `ONMARU_STATE_DIR`, `STATE_DIRECTORY` | (없음) | 대시보드 설정을 저장할 디렉터리입니다(사용자 설정 `users/<사용자 이름>.json`, 전역 설정 `site.json`, 배경 이미지 `images/`). 비워 두면 메모리에만 보관하므로 재시작하면 사라집니다. systemd의 `StateDirectory=`가 `STATE_DIRECTORY`를 넘겨줍니다. |
| `-smart-refresh-at` | `ONMARU_SMART_REFRESH_AT` | `00:00` | SMART 정보를 하루 한 번 다시 가져오는 기준 시각입니다(`HH:MM`, 서버 로컬 시간). 마지막 조회가 이 시각 이전이면 다음 접속 때 다시 가져옵니다. SMART 조회는 대기 중인 디스크를 깨우므로 자동 주기 조회는 하지 않습니다. |
| `-workbench-url` | `ONMARU_WORKBENCH_URL` | (없음) | 브라우저에서 OMV 웹 UI(workbench)를 열 주소입니다. 아래 "OMV 워크벤치 열기"를 참고해 주세요. 비워 두면 "OMV 워크벤치" 앱과 프로필 메뉴 항목이 보이지 않습니다. |
| `-helper-socket` | `ONMARU_HELPER_SOCKET` | (없음) | 권한 도우미 소켓의 절대 경로입니다(설치 스크립트는 `/run/onmaru-helper/helper.sock`). 비워 두면 도우미를 쓰는 기능이 꺼집니다. 아래 "권한 도우미"를 참고해 주세요. |
| `-terminal` | `ONMARU_TERMINAL` | `false` | 웹 터미널을 허용합니다. 설정 앱의 "서버" 페이지에서도 켜고 끌 수 있습니다. 아래 "웹 터미널"을 참고해 주세요. |
| `-ssh-addr` | `ONMARU_SSH_ADDR` | `auto` | 웹 터미널이 접속할 SSH 서버 주소입니다. `auto`는 `/etc/ssh/sshd_config`의 `Port`로 `127.0.0.1`에 접속하므로 OMV에서 포트를 바꿔도 따라갑니다. 직접 적을 때는 루프백 `IP:포트`만 받습니다. |
| `-ssh-host-keys` | `ONMARU_SSH_HOST_KEYS` | `/etc/ssh/ssh_host_*_key.pub` | 웹 터미널이 받아들일 SSH 서버 호스트 공개 키 파일의 glob 패턴입니다. 서버 키가 이 중 하나와 같을 때만 접속합니다. 보통은 바꾸지 않습니다. |
| `-public-origin` | `ONMARU_PUBLIC_ORIGIN` | (없음) | 브라우저가 대시보드에 접속하는 공개 HTTPS 주소입니다(`https://호스트[:포트]`, 경로 없이). 보안 강화 모드의 패스키에 씁니다. 브라우저가 믿는 인증서의 도메인 이름이어야 하며 IP 주소는 받지 않습니다. 비워 두면 패스키를 쓸 수 없고 인증 앱(TOTP)과 복구 코드만 씁니다. 아래 "보안 강화 모드"를 참고해 주세요. |

세션은 백엔드 메모리에만 있으므로 백엔드를 재시작하면 모든 사용자가 다시 로그인해야 합니다. `/var/lib/onmaru`에는 대시보드 자신의 상태만 들어 있으며 OMV 설정과는 관계가 없습니다. 백업할 때 이 디렉터리를 함께 복사하면 사용자 설정, 전역 설정, 올린 배경 이미지가 유지됩니다.

### OMV 워크벤치 열기

`-workbench-url`을 설정하면 "모든 앱"·바탕화면 바로가기의 "OMV 워크벤치"와 프로필 메뉴의 "OMV 워크벤치 열기"가 OMV 웹 UI를 브라우저의 새 탭으로 엽니다.

- 값은 브라우저에서 OMV에 접속하는 주소입니다(예: `https://nas.example.lan/`). `http://`·`https://`로 시작하는 주소 또는 대시보드 기준 경로(`/`, `./`, `../`)를 받습니다. 대시보드를 OMV와 같은 호스트의 경로 접두사(예: `/desk/`) 아래에 두었다면 `/`도 됩니다. 쿼리·프래그먼트는 받지 않으며, `nas.example.lan/`처럼 `http(s)://`가 없는 주소는 거부합니다.
- 같은 탭을 다시 씁니다. 이미 연 OMV 탭이 있으면 새 탭을 만들지 않고 그 탭에서 OMV 첫 화면으로 이동합니다.
- OMV 로그인은 그 탭에서 따로 합니다. OMV는 탭마다 로그인 상태를 따로 두고 비밀번호 없이 로그인하는 방법을 제공하지 않으므로, 대시보드 로그인을 OMV 탭에 넘길 수 없습니다. 탭을 닫지 않고 다시 쓰는 동안에는 로그인이 유지됩니다. 처음 로그인하는 브라우저라면 OMV가 "새 브라우저 로그인" 알림 메일을 보낼 수 있습니다.
- 대시보드 안의 창(iframe)으로 띄우지 않는 이유: OMV 웹 UI는 `X-Frame-Options: SAMEORIGIN`을 보내므로 대시보드와 출처(호스트·포트)가 같을 때만 iframe에 들어갈 수 있습니다. 보안 헤더를 끄는 방식은 쓰지 않습니다.

## 권한 도우미

권한 도우미(`onmaru-helper`)는 root로 도는 별도 서비스입니다. 대시보드 자신은 권한이 없는 전용 사용자로 돌고 권한을 올릴 수 없으므로(`NoNewPrivileges=yes`), 다음 일은 도우미를 거칩니다.

- **사용자 권한 연산**: 로그인한 사용자 자신의 Linux 계정(uid, 기본 그룹, 보조 그룹)으로 파일을 읽고 씁니다. 실제로 열 수 있는지는 커널이 소유권과 ACL로 판단하므로 SSH로 접속할 때와 같은 권한이 적용됩니다. OMV 공유 폴더의 권한(Privileges) 설정은 SMB·FTP 같은 서비스에만 적용되고 여기에는 적용되지 않으므로, 막으려면 OMV에서 공유 폴더의 ACL을 바꿉니다. 대상은 그 사용자의 홈 디렉터리와 `/srv` 아래에 마운트된 데이터 파일시스템뿐입니다. 파일 탐색기 같은 기능이 이것을 쓰고, 웹 터미널의 일회용 SSH 키(아래 "웹 터미널")도 이 권한으로 넣고 지웁니다.
- **root 권한 연산**: 관리자가 비밀번호를 다시 입력하면 그 대시보드 세션에서 5분 동안 정해진 root 연산을 쓸 수 있습니다(sudo와 비슷합니다). 임의의 명령을 실행하는 기능은 없고, 기능마다 필요한 연산만 따로 만들어 둡니다. 지금은 실행 권한 확인(`id`), 대시보드에서 업그레이드의 업그레이드 요청(`upgrade.apply`), 파일 탐색기의 디스크 휴지통 만들기(`trash.prepare`)가 있습니다.

설치 스크립트가 기본으로 설치합니다. 질문에서 설치하지 않기로 하거나 `--no-helper`를 주면 설치하지 않으며, 이때 도우미가 필요한 기능은 쓸 수 없지만 나머지 기능은 그대로 쓸 수 있습니다. 설치 상태와 지금 세션의 실행 권한, 권한 상승은 관리자가 설정 앱의 "서버" 페이지에서 확인할 수 있습니다.

### 보안 설계

도우미는 대시보드의 말을 그대로 믿지 않습니다. 대시보드가 뚫려도 곧바로 root나 모든 사용자의 권한이 되지 않게 하기 위해서입니다.

- 소켓(`/run/onmaru-helper/helper.sock`, 권한 `0600`)에는 대시보드 서비스 사용자만 접속할 수 있고, 도우미가 접속한 프로세스의 uid(`SO_PEERCRED`)를 다시 확인합니다. Docker 프록시에 마운트하는 `/run/onmaru`와는 다른 디렉터리입니다.
- 로그인할 때 대시보드가 받은 비밀번호를 도우미가 `unix_chkpwd`로 직접 확인한 뒤에만 그 세션에 티켓을 발급합니다. 티켓은 도우미 메모리에만 있으며, 로그아웃·세션 만료 때 폐기되고 도우미나 대시보드가 다시 시작하면 모두 사라집니다. 2단계 인증을 쓰는 계정은 인증을 마친 뒤에야 티켓을 쓸 수 있습니다.
- 티켓을 주는 계정은 OMV 로그인과 같은 기준입니다. root는 받지 않고, `openmediavault-admin` 그룹이거나 일반 사용자 uid 범위(`/etc/login.defs`의 `UID_MIN`~`UID_MAX`)여야 합니다.
- root 권한 상승은 `openmediavault-admin`과 상승 그룹(기본값 `sudo`, 설치할 때 `--elevate-group`으로 바꿈) 모두에 속한 사용자만, 비밀번호를 다시 입력해야 할 수 있습니다. 상승은 그 세션에만 붙고 5분 뒤 끝나며(연산을 해도 늘어나지 않습니다), 서버 페이지에서 바로 끝낼 수 있습니다. 상승 그룹을 `openmediavault-admin`으로 정하면 OMV 관리자는 모두 상승할 수 있습니다.
- 비밀번호 확인은 사용자마다 5분 안에 3번 틀리면 30초부터 두 배씩 최대 15분 동안 잠깁니다. `unix_chkpwd`는 PAM의 실패 잠금(`pam_faillock`)을 거치지 않으므로 이 잠금으로 계정이 영구히 잠기지는 않습니다.
- 연산은 매번 자식 프로세스로 실행하며, 사용자 권한 연산은 시작하기 전에 그 사용자로 권한을 내립니다. root 프로세스는 파일 내용을 다루지 않습니다.
- systemd 유닛은 root여도 권한을 좁혀 둡니다. 사용자 권한으로 내리고 자기 자식 프로세스를 멈추는 권한(`CAP_SETUID`, `CAP_SETGID`, `CAP_KILL`)만 남기고, 네트워크를 쓰지 않으며(`PrivateNetwork=yes`), 파일시스템은 `/srv`와 `/home`, 대시보드에서 업그레이드를 켰을 때의 요청 디렉터리(`/run/onmaru-upgrade`) 말고는 읽기 전용입니다.
- 업그레이드 요청(`upgrade.apply`)은 대상 커밋(40자리 16진수)과 새 버전이 물은 설정의 이름·값(길이와 문자를 제한)만 받아 요청 파일로 업그레이드 서비스에 넘깁니다. 명령이나 경로는 받지 않으며, 진행할 수 있는지는 업그레이드 서비스가 확인 결과와 저장소 상태로 다시 확인합니다.
- 디스크 휴지통 만들기(`trash.prepare`)는 `/srv` 아래 마운트 지점 하나만 받아 그 맨 위에 `.Trash` 폴더(1777)를 만듭니다. 이미 있는 `.Trash`가 심볼릭 링크이거나 root 소유가 아니면 거절하므로, 사용자가 미리 둔 링크를 따라가 다른 폴더의 권한을 바꾸지 않습니다.
- 비밀번호와 티켓은 기록하지 않습니다. 도우미는 비밀번호 확인 결과, 모든 root 연산, 파일 쓰기 연산(경로 포함)을 `journalctl -u onmaru-helper`에 남깁니다. 파일 읽기는 경로 없이 연산과 결과만 남깁니다.

남는 위험도 있습니다. 대시보드가 뚫리면 공격자는 그때 로그인해 있는 사용자의 티켓을 쓸 수 있고, 그 뒤에 입력되는 비밀번호를 가로챌 수 있습니다. OMV 관리자는 원래 OMV 웹 UI로 root와 같은 일을 할 수 있으므로, 도우미의 root 권한 상승이 관리자에게 새로운 권한을 주지는 않습니다.

대시보드에서 업그레이드를 켜면 상승한 세션으로 할 수 있는 일이 "설치된 저장소로 업그레이드"까지 넓어집니다. 업그레이드는 저장소에서 빌드한 코드를 root로 실행하므로, 저장소를 바꿀 수 있는 계정(저장소 소유자)은 SSH로 `./install.sh`를 실행할 때와 마찬가지로 업그레이드를 통해 root로 코드를 실행할 수 있습니다. 저장소 소유자 계정은 관리자 계정처럼 다루고, 업그레이드하기 전에 확인 화면의 커밋 목록을 봐 주세요. 확인 요청에는 상승이 필요 없으므로 대시보드가 뚫리면 확인을 계속 요청할 수 있지만, 그때 하는 일은 저장소 소유자 계정의 `git fetch`와 임시 빌드뿐입니다. 이 기능이 필요 없다면 `--no-web-upgrade`로 꺼 둡니다.

### 제한

- 계정은 로컬 `/etc/passwd`·`/etc/group`과 `/etc/shadow`(`unix_chkpwd`)로만 확인합니다. LDAP 플러그인 등으로 들어오는 계정은 대시보드에는 로그인할 수 있지만 도우미 티켓은 받지 못합니다.
- 홈 디렉터리가 `/home`이나 `/srv` 아래가 아니면 읽기만 할 수 있습니다(유닛의 `ReadWritePaths=`).

### 설치 확인

```sh
systemctl status onmaru-helper.socket
```

로그인한 뒤 설정 앱의 "서버" 페이지에서 "실행 권한"이 내 계정의 uid로 나오는지, 권한 상승 뒤 "실행 권한(root)"이 uid 0으로 나오는지 확인합니다. 도우미가 받은 요청과 결과는 다음 명령으로 봅니다.

```sh
journalctl -u onmaru-helper -e
```

도우미 유닛의 보안 설정은 `systemd-analyze security onmaru-helper`로 점검할 수 있습니다.

## 파일 탐색기

"모든 앱"과 바탕화면의 "파일"은 홈 폴더와 OMV 공유 폴더를 둘러보는 창입니다. 파일은 권한 도우미가 로그인한 사용자의 권한으로 다루므로, 도우미를 설치하지 않았으면 창을 열 때 그 이유를 안내하고 쓸 수 없습니다(위 "권한 도우미"). openmediavault-filebrowser 플러그인은 계정을 따로 두고 폴더 하나를 보이지만, 온마루는 OMV 계정을 그대로 쓰고 로그인 한 번으로 모든 공유 폴더를 사용자별 파일 시스템 권한으로 보입니다.

- 처음에는 홈 폴더와 공유 폴더가 보입니다. 일반 사용자의 세션으로는 OMV의 공유 폴더 목록을 받을 수 없으므로, 관리자가 로그인할 때 받은 목록을 이름표로 저장해 씁니다. 공유 폴더를 더하거나 바꾼 뒤에는 관리자가 다시 로그인하거나 설정 앱 "서버" 페이지의 "파일 탐색기"에서 "지금 받기"를 눌러 주세요. 받은 적이 없으면 `/srv` 아래 디스크를 대신 보입니다.
- 무엇을 읽고 쓸 수 있는지는 파일 시스템 권한(소유자, 모드, ACL)만 따릅니다. OMV 공유 폴더 권한(Privileges)은 SMB·FTP에만 적용되므로, 막으려면 OMV에서 공유 폴더의 ACL을 바꿔 주세요. 파일을 누르면 열리는 정보 패널에서 소유자·그룹·모드·ACL 유무와 내 권한을 볼 수 있고, 관리자에게는 OMV의 ACL 편집 화면 링크가 함께 나옵니다. 관리자도 자기 계정의 파일 시스템 권한으로 봅니다.
- 관리자가 설정 앱 "서버" 페이지에서 "디스크 최상위 보기"를 켜면 관리자에게 공유 폴더 밖, `/srv` 아래 디스크의 맨 위까지 보입니다(기본 꺼짐). 루트 파일시스템의 공유 폴더(openmediavault-sharerootfs, 예: `/kvm`)는 아직 열 수 없습니다.
- 수만 개가 든 폴더도 바로 열립니다. 이름을 먼저 읽고, 보이는 줄의 정보만 읽기 때문입니다. 한 폴더에 30만 개가 넘으면 일부만 보입니다. 수정한 날짜·크기순 정렬은 모든 항목의 정보를 읽은 뒤에 바뀌며, 읽는 동안 진행 막대와 취소 단추가 나옵니다. 이름순은 코드포인트 순서(숫자는 크기 순서)입니다.
- 내려받기는 정보 패널의 "내려받기"나 파일의 우클릭 메뉴로 합니다. 브라우저의 내려받기 관리자가 받으므로 끊긴 내려받기를 이어 받을 수 있습니다.
- "올리기"로 파일을 여러 개 골라 지금 폴더에 올립니다. 같은 이름의 파일이 있으면 덮어쓸지 묻습니다. 덮어쓰면 새 파일로 바뀌므로 소유자는 올린 사용자가 되고(권한 비트는 되도록 유지), 폴더에 쓸 수 있으면 쓰기 권한이 없는 파일도 덮어쓸 수 있습니다(리눅스에서 폴더에 쓸 수 있으면 그 안의 파일을 지우고 다시 만들 수 있는 것과 같습니다). 파일은 하나씩 차례로 올리고, 받는 동안은 같은 폴더의 임시 파일(`.onmaru-upload-…`)에 썼다가 다 받으면 이름을 바꿉니다. 올리기가 길어지면 "파일 작업" 창에 올린 양, 속도, 남은 시간이 보입니다. 올리는 동안에는 입력이 없어도 세션이 연장되고, 탐색기 창을 닫아도 올리기는 이어집니다. "파일 작업" 창을 닫거나 페이지를 떠나면 올리기가 취소됩니다. 올리지 못했거나 취소된 파일은 그 창에서 다시 올릴 수 있습니다.
- 컴퓨터의 파일을 창으로 끌어 와도 올립니다. 폴더 줄 위에 놓으면 그 폴더에, 빈 곳에 놓으면 지금 폴더에 올립니다. 폴더는 아직 끌어 와서 올릴 수 없으며, 함께 끌어 온 폴더는 건너뛰고 알려 줍니다.
- 전송은 60초 동안 진행이 없으면 끊기고, 한 번에 6시간까지입니다. 이미 시작한 내려받기·올리기는 로그아웃하거나 보안 정책을 올려도 끝까지 갑니다.
- 도구 막대의 "폴더 만들기", 우클릭 메뉴의 "이름 바꾸기"(F2)와 "삭제"(Delete)로 폴더를 만들고 이름을 바꾸고 지웁니다. 빈 곳을 우클릭하면 폴더 만들기와 올리기, 모두 선택이 나옵니다. Ctrl(macOS는 ⌘)이나 Shift를 누른 채 누르면 여러 항목을 고르고, Ctrl+A로 모두 고릅니다. 정보 패널에도 이름 바꾸기와 삭제 단추가 있습니다.
- 삭제하면 휴지통으로 옮깁니다. 서버의 trash-cli(`trash-put`)와 같은 곳·형식의 휴지통이라 서버에서 `trash-list`, `trash-restore`, `trash-empty`로도 같은 휴지통을 다룰 수 있습니다. 홈 폴더의 항목은 홈 휴지통(`~/.local/share/Trash`)에, 디스크의 항목은 그 디스크 맨 위의 `.Trash/<uid>`나 `.Trash-<uid>`에 들어가며, 다른 디스크로 복사하지는 않습니다. SMB 휴지통(`.recycle`)과는 따로입니다.
  - 확인 대화상자에서 "영구 삭제…"를 고르거나 Shift+Delete를 누르면 휴지통을 거치지 않고 지웁니다. 영구 삭제는 되돌릴 수 없으며, 폴더는 안의 파일과 폴더까지 모두 지웁니다.
  - OMV 데이터 디스크의 맨 위는 보통 root 소유라 사용자가 휴지통 폴더를 만들 수 없습니다. 이런 디스크에서는 지우기 전에 영구 삭제라고 알립니다. 관리자가 설정 앱 "서버" 페이지의 "파일 탐색기"에서 디스크마다 "휴지통 만들기"를 누르면(root 권한 상승이 필요합니다) 그 디스크 맨 위에 모든 사용자가 쓰는 `.Trash` 폴더(1777)가 생기고, 그 뒤로는 휴지통으로 옮깁니다.
  - 사이드바 끝의 "휴지통"에서 항목을 원래 위치·지운 날짜와 함께 보고, 되돌리거나 영구 삭제하거나 휴지통을 비웁니다. 원래 위치에 같은 이름이 있으면 되돌릴 때 새 이름을 묻습니다. 고른 항목을 사이드바의 "휴지통"에 끌어 놓아도 휴지통으로 옮깁니다.
- 고른 항목을 끌어 폴더 줄, 위쪽 경로, 사이드바의 폴더, 다른 탐색기 창에 놓으면 옮깁니다. 다른 탐색기 창에서는 폴더 줄이 아닌 빈 곳이나 파일 줄에 놓아도 그 창이 보고 있는 폴더로 옮깁니다. 다른 디스크(홈 폴더와 데이터 디스크는 서로 다른 디스크로 봅니다)에 놓으면 옮기지 않고 복사하며, 끄는 동안 이름표에 "복사"로 표시합니다. 읽기만 가능한 폴더의 항목도 다른 디스크로는 복사할 수 있습니다. 옮기거나 복사할 곳에 같은 이름이 있으면 그 항목은 건너뛰고 알려 줍니다. 마우스와 펜으로 끌 수 있고, 터치에서는 끌지 않습니다.
  - 복사가 길어지면 "파일 작업" 창이 열려 복사한 양, 파일 수, 속도, 남은 시간을 보입니다. 모두 복사하면 창이 스스로 닫히고, 복사하지 못한 항목이 있으면 이유와 함께 남겨 둡니다. 창에서 복사를 취소하거나 창을 닫으면 복사하던 항목은 지우고 멈추며, 이미 복사한 항목은 남습니다. 탐색기 창을 닫아도 복사는 이어집니다.
  - 복사는 내용과 수정한 날짜만 옮깁니다. 권한·소유자·ACL은 올리기와 같이 복사할 폴더의 기본값을 따르고, 심볼릭 링크는 링크로 만들며, 폴더 안의 특수 파일(FIFO, 소켓, 장치)은 건너뜁니다.
- 여러 항목을 지우거나 옮기면 하나씩 차례로 하며, 오래 걸리면 진행 막대와 "중지" 단추가 나옵니다. 중지하면 하던 항목까지 마치고 멈춥니다. 폴더 하나를 지우는 데 10분이 넘으면 멈추므로, 다시 지우면 남은 항목을 이어서 지웁니다.
- 사이드바에 보이는 폴더(홈 폴더, 공유 폴더, 디스크)와 그것을 품은 폴더는 이름을 바꾸거나 옮기거나 지울 수 없습니다. 디스크 최상위 보기에서 공유 폴더를 실수로 지우지 않게 하기 위해서입니다. 공유 폴더는 OMV에서 다뤄 주세요.
- 창은 여러 개 열 수 있습니다. 두 폴더를 나란히 볼 때 씁니다. 한 창에서 폴더 안을 바꾸면 같은 폴더를 보는 다른 창도 바로 바뀝니다.
- 권한 도우미의 감사 로그(`journalctl -u onmaru-helper`)에는 내려받기(결과만)와 쓰기 작업(올리기, 폴더 만들기, 이름 바꾸기·옮기기, 복사, 삭제, 휴지통으로 옮기기·되돌리기·영구 삭제·비우기)만 남고, 쓰기 작업은 경로도 남습니다(복사는 원본 폴더, 항목 수, 대상 폴더). 폴더 목록, 정보 읽기, 휴지통 목록은 남지 않습니다.

## 웹 터미널

"모든 앱"의 "터미널"은 대시보드에 로그인한 계정으로 이 NAS의 SSH 서버(sshd)에 접속한 셸을 창 안에 엽니다. 대시보드가 같은 호스트의 SSH 서버(`127.0.0.1`)에 SSH로 접속해 화면을 중계하므로, 누가 어떤 방법으로 들어갈 수 있는지는 OMV의 SSH 설정이 그대로 정합니다.

- 기본으로 꺼져 있습니다. 관리자가 설정 앱의 "서버" 페이지에서 "웹 터미널"을 켜거나 `ONMARU_TERMINAL=true`로 켭니다. 끄면 열려 있던 터미널도 바로 닫힙니다.
- OMV에서 SSH 서비스가 켜져 있어야 하고, 계정이 SSH 로그인을 허용한 그룹(OMV 기본값 `_ssh`)에 있어야 합니다. 그룹은 OMV 웹 UI의 사용자 편집 화면에서 더할 수 있습니다. OMV 기본 관리자 계정(`admin`)은 셸이 없어 쓸 수 없습니다. 다른 계정이나 root로 접속하는 기능은 없으며, root 작업은 셸 안에서 `sudo`로 합니다.
- 인증
  - 권한 도우미가 있으면 비밀번호를 다시 묻지 않습니다. 접속할 때마다 대시보드가 메모리에서 일회용 키를 만들고, 도우미가 사용자 권한으로 `~/.ssh/authorized_keys`에 그 키를 2분 동안 이 호스트 안의 접속에만 쓸 수 있는 줄(`restrict,pty,from="127.0.0.1,::1",expiry-time=…`, 주석 `onmaru-ephemeral`)로 넣었다가 인증이 끝나면 바로 지웁니다. 공개 키만 받는 SSH 설정(OMV의 "Password authentication" 끔)에서도 됩니다.
  - 도우미가 없거나 키를 쓸 수 없으면 SSH 서버가 묻는 비밀번호(와 2단계 인증 코드)를 터미널 안에서 입력합니다. 비밀번호는 저장하지 않고 SSH 서버로 바로 넘깁니다.
  - 홈 디렉터리에 그룹이나 다른 사용자의 쓰기 권한이 있으면 SSH 서버(`StrictModes`)가 그 안의 키를 무시하므로 일회용 키를 쓸 수 없습니다. 그 권한을 빼거나(`chmod go-w <홈 디렉터리>`) 비밀번호로 접속해 주세요.
- 도우미 없이 공개 키만 받는 SSH 서버를 쓴다면, 이 호스트 안의 접속에만 비밀번호를 허용할 수 있습니다. OMV 웹 UI의 SSH 설정 "추가 옵션"에 다음을 넣습니다. 추가 옵션은 `Include /etc/ssh/sshd_config.d/*.conf` 바로 앞에 들어가므로, 마지막 `Match all`이 없으면 그 뒤의 `Include`까지 이 조건 안에 들어갑니다.

  ```
  Match Address 127.0.0.1,::1
      PasswordAuthentication yes
  Match all
  ```

- 터미널 창은 여러 개 열 수 있습니다. "모든 앱"이나 바로가기의 터미널 아이콘을 누를 때마다 새 창이 열리고, 작업표시줄의 터미널 버튼을 우클릭(터치는 길게 누르기)해 "새 창"을 골라도 됩니다. 창마다 셸이 따로 열리고, 한 대시보드 세션에서 동시에 연 창은 다른 탭의 창을 합쳐 4개까지입니다.
- 한 대시보드 세션(로그인한 브라우저)은 SSH 연결 하나를 함께 쓰므로, 새 창이나 다른 탭에서 터미널을 열 때는 다시 묻지 않습니다. 창을 닫거나, 로그아웃하거나, 세션이 만료되면 셸이 끝납니다. 터미널에 입력하는 동안에는 세션이 연장되지만 출력만 나오는 동안에는 연장되지 않으므로, 오래 걸리는 작업은 `tmux`나 `screen` 안에서 실행해 주세요.
- 복사는 Ctrl+Shift+C, 붙여 넣기는 Ctrl+Shift+V입니다.

### 웹 터미널의 보안

- 대시보드는 SSH 서버의 클라이언트일 뿐입니다. SSH 서버는 원래 LAN에 열려 있으므로 대시보드가 뚫려도 새로 얻는 권한은 없고, 로그인 기록·PAM 세션·`AllowGroups` 같은 SSH 정책도 그대로 적용됩니다. 호스트 키는 `/etc/ssh/ssh_host_*_key.pub`와 비교해 같은 서버에만 접속합니다.
- 일회용 키는 도우미의 기존 파일 쓰기 권한(로그인한 사용자 자신의 홈) 안의 일이라 새 권한을 더하지 않습니다. 도우미는 키 줄을 직접 만들고(옵션을 대시보드가 정할 수 없습니다) ed25519 공개 키만 받으며, `journalctl -u onmaru-helper`에는 키 지문만 남깁니다. 지우지 못한 줄도 2분 뒤에는 SSH 서버가 받지 않고 다음 접속 때 지워집니다.
- SSH 서버와 fail2ban에는 접속지가 `127.0.0.1`로만 보입니다. 그래서 대시보드가 웹 터미널의 비밀번호 실패를 브라우저 IP·사용자 이름별로 따로 세어 잠급니다(로그인과 같은 기준). 대시보드 로그(`journalctl -u onmaru`)에는 사용자, 브라우저 IP, 결과만 남습니다.

## 보안 강화 모드

웹 터미널, root 권한 상승, 파일 탐색기처럼 보안에 민감한 기능을, 확인을 한 번 더 거친 세션에서만 쓰게 합니다. 열어 둔 브라우저나 빼앗긴 세션 쿠키, 새어 나간 비밀번호만으로는 그 기능을 쓰지 못하게 하는 것이 목적입니다. 기본으로 꺼져 있습니다.

- 관리자가 설정 앱의 "보안 정책" 페이지에서 기능마다 단계를 고릅니다.
  - **끔**: 따로 확인하지 않습니다.
  - **비밀번호 재확인**: 그 세션에서 비밀번호를 한 번 더 입력해야 합니다. 로그인할 때 넣은 비밀번호는 치지 않습니다.
  - **2차 인증**: 패스키, 인증 앱(TOTP), 복구 코드 중 하나로 확인해야 합니다. OpenMediaVault의 2차 인증으로 로그인한 세션도 2차 인증을 거친 것으로 봅니다.
- 파일 탐색기는 기본으로 폴더 보기와 내려받기까지 확인합니다. 같은 페이지의 "파일 탐색기 확인 범위"를 "쓰기·삭제에만"으로 바꾸면 보기와 내려받기는 확인 없이 쓰고, 올리기·폴더 만들기·이름 바꾸기·옮기기·삭제·휴지통 작업 전에만 확인합니다. 범위를 바꾸려면 그 단계를 거친 세션이어야 합니다.
- 같은 페이지에서 패스키로 로그인의 만료 기간(7·30·90·180·365일, 기본 30일)도 고릅니다. 바꾸려면 그 세션에서 비밀번호를 다시 확인했거나 2차 인증을 거쳤어야 합니다(아래 "패스키로 로그인").
- 확인은 그 세션에 남습니다. 로그아웃하거나 세션이 만료될 때까지(OMV 자동 로그아웃 시간 동안 입력이 없을 때까지) 다시 묻지 않습니다. OMV 자동 로그아웃을 끄면 확인한 세션이 로그아웃할 때까지 남으므로 보안 정책 페이지가 경고를 보입니다.
- 2차 인증을 요구하는 기능이 있으면, 인증 수단을 등록한 사용자에게는 로그인 직후 2차 인증을 권합니다. 수단이 없는 기기라면 건너뛸 수 있고, 그 기능을 열 때 같은 확인 창이 나옵니다.
- 정책을 바꾸는 관리자도 바꾸는 기능의 이전·새 단계 중 높은 쪽을 거친 세션이어야 합니다. 세션을 빼앗은 쪽이 정책을 내리고 기능을 여는 것을 막기 위해서입니다. 정책을 올리면 조건을 채우지 못하는 세션의 웹 터미널은 바로 닫히고 root 권한 상승도 끝납니다. 파일 탐색기는 다음 요청부터 막히고(쓰기·삭제에만 적용하지 않았다면 목록과 내려받기 포함) 창에 확인 단추가 나옵니다. 쓰기·삭제에만 적용하면 쓰기 작업을 할 때 확인 창이 나오고, 확인하면 그 작업을 이어서 합니다. 이미 시작한 전송은 끝까지 갑니다.

### 인증 수단 등록

각 사용자가 설정 앱의 "보안" 페이지에서 등록합니다. 등록·삭제와 복구 코드 다시 만들기는 비밀번호와(이미 등록한 수단이 있으면) 그 수단을 다시 확인한 뒤 5분 동안 할 수 있습니다. 새 기기에서 패스키를 추가할 때는 그 수단 대신 기기 추가 코드도 받습니다(아래 "새 기기에 패스키 추가").

- **패스키**: 기기의 화면 잠금(지문, 얼굴, PIN)이나 보안 키로 확인합니다. 가장 권하는 방법입니다. 공개 주소(`-public-origin`, `ONMARU_PUBLIC_ORIGIN`)를 설정해야 하고, 브라우저가 믿는 인증서의 HTTPS 도메인으로 대시보드에 접속해야 합니다. IP 주소나 자체 서명 인증서로는 쓸 수 없고, 공개 주소를 바꾸면 패스키를 다시 등록해야 합니다.
  - 등록할 때 새 패스키로 한 번 더 확인합니다. 패스키 저장소가 이 확인에 사용자 확인(PIN, 생체 인식)을 알려 주지 않으면 등록하지 않습니다. 잠금이 풀려 있으면 확인을 건너뛰는 비밀번호 관리자나, Windows에서 "이 장치에 패스키 저장"을 꺼 두어 Microsoft Password Manager에만 저장되는 패스키가 그런 예입니다. 브라우저 창에서 이 기기(Windows Hello 등)나 보안 키를 골라 다시 등록해 주세요.
  - 등록하지 않은 패스키는 브라우저가 지원하면 저장소에서 지우게 합니다. 지원하지 않으면 안내에 따라 패스키 저장소에서 직접 지워 주세요.
  - iCloud 키체인, 비밀번호 관리자처럼 여러 기기에 동기화되는 패스키는 보안 페이지 목록에 "동기화됨"으로 표시합니다. 막지는 않습니다.
- **인증 앱(TOTP)**: Google Authenticator, 2FAS 같은 앱의 6자리 코드입니다. QR 코드를 찍거나 키를 입력해 등록하며, 공개 주소 없이도 쓸 수 있습니다.
- **복구 코드**: 첫 수단을 등록할 때 10개를 만들어 한 번만 보여 줍니다. 코드마다 한 번씩 쓸 수 있고, 보안 페이지에서 다시 만들 수 있습니다.

### 새 기기에 패스키 추가

새 기기에는 다른 기기에서 만든 패스키가 없는 경우가 많습니다. 그래서 패스키를 추가할 때의 본인 확인은 인증 앱이 있으면 인증 앱을, 없으면 기기 추가 코드를 먼저 묻습니다. iCloud 키체인처럼 동기화되는 패스키나 휴대전화의 패스키는 "패스키 사용"을 눌러 그대로 확인할 수 있습니다.

- **기기 추가 코드 만들기**: 패스키가 있는 기기의 보안 페이지에서 "다른 기기에 패스키 추가"의 "코드 만들기"를 누릅니다. 그 기기에서도 비밀번호와 등록한 수단을 다시 확인합니다.
- **새 기기에서 쓰기**: 보안 페이지의 "패스키 추가"를 누르고, 본인 확인에서 비밀번호와 이 코드를 입력합니다.
- 코드는 10분 동안 한 번만 쓸 수 있고, 새로 만들면 이전 코드는 쓸 수 없습니다. 복구 코드와 달리 남은 복구 코드 수는 줄지 않습니다.
- 코드로 마친 본인 확인은 패스키 추가뿐 아니라 수단 삭제와 복구 코드 다시 만들기도 5분 동안 할 수 있게 합니다. 코드를 다른 사람에게 알려 주지 마세요.
- 코드로 본인 확인을 마친 세션은 2차 인증을 거친 것으로 보지 않습니다. 새 패스키를 등록하면 그때 2차 인증을 거친 세션이 됩니다.

### 패스키로 로그인

등록한 패스키로 비밀번호를 입력하지 않고 로그인합니다. 브라우저마다 따로 켜며, 보안 정책의 단계와 상관없이 쓸 수 있습니다. 패스키와 같은 조건(공개 주소, 브라우저가 믿는 HTTPS 도메인)이 필요하고, 패스키가 PRF 확장을 지원해야 합니다. PRF를 지원하지 않는 패스키로는 켤 수 없으며, 2차 인증에만 씁니다. 보안 키처럼 패스키를 만들 때 PRF도 함께 만들어야 하는 저장소에서는 이 기능이 생기기 전에 등록한 패스키에 PRF가 없을 수 있으니, 패스키를 다시 등록해 주세요.

- **켜기**: 패스키를 등록한 사용자가 비밀번호로 로그인하면, 로그인 직후 "이 브라우저에서 다음부터 패스키로 로그인"을 권합니다. 패스키로 한 번 확인하면 켜집니다. 설정 앱의 "보안" 페이지에서도 비밀번호와 패스키를 확인해 켤 수 있습니다. 한 사용자가 켤 수 있는 브라우저는 20개까지입니다.
- **로그인**: 로그인 화면의 "패스키로 로그인" 단추를 누르고 패스키로 확인합니다. 이 세션은 2차 인증을 거친 세션이므로 2차 인증을 요구하는 기능도 다시 묻지 않습니다. OpenMediaVault의 2차 인증을 쓰는 계정은 그 확인을 그대로 거칩니다.
- **키 조각 회전**: 패스키로 로그인할 때마다 대시보드가 키 조각을 바꾸고, 브라우저는 저장한 비밀번호를 새 조각으로 다시 암호화합니다. 그래서 브라우저 프로필을 복사해 간 사본은 그 브라우저에서 한 번 더 로그인하면 쓸 수 없고, 그런 사본으로 로그인을 시도하면 대시보드가 그 등록을 지우므로 원래 브라우저에서도 비밀번호로 로그인한 뒤 다시 켜야 합니다. 반대로 사본이 먼저 쓰이면 원래 브라우저의 다음 패스키 로그인이 "풀 수 없음"으로 실패하고 등록이 지워집니다. 원래 브라우저에서 갑자기 이 오류가 나오면 누군가 사본을 썼을 수 있으니, 비밀번호를 바꾸고 패스키를 둔 기기를 확인해 주세요.
- **만료**: 켠 날부터 관리자가 "보안 정책" 페이지에서 고른 기간(기본 30일)이 지나면 만료됩니다. 패스키로 로그인해도 기간은 늘어나지 않습니다. 관리자가 기간을 줄이면 이미 켠 브라우저에도 바로 적용되고, 늘리면 새로 켠 브라우저부터 적용됩니다. 만료되면 비밀번호로 로그인한 뒤 다시 켜 주세요.
- **비밀번호 변경**: 저장해 둔 비밀번호로는 로그인할 수 없으므로, 그 브라우저에서 패스키로 로그인하면 실패를 알리고 등록을 지웁니다. 비밀번호로 로그인한 뒤 다시 켜 주세요. 다른 브라우저의 등록도 그 브라우저에서 쓸 때 지워지며, 바로 정리하려면 보안 페이지에서 해제해 주세요.
- **해제**: 보안 페이지의 "패스키로 로그인하는 브라우저" 목록에 브라우저마다 패스키 이름, 켠 날, 마지막 사용, 만료일이 나오고, 지금 쓰는 브라우저에는 "이 브라우저"가 붙습니다. 로그인 방법을 줄이기만 하므로 비밀번호나 수단을 다시 확인하지 않고 바로 해제할 수 있습니다. 그 패스키를 지우거나 관리자가 사용자의 수단을 초기화해도 함께 지워집니다.

### 복구

- 수단을 잃은 사용자는 복구 코드로 확인한 뒤 새 수단을 등록합니다.
- 복구 코드도 없으면 2차 인증을 거친 관리자가 보안 정책 페이지의 "사용자의 로그인 수단"에서 그 사용자의 수단을 초기화합니다. 그 사용자의 세션은 끝나고, 다시 로그인한 뒤 새로 등록할 수 있습니다.
- 관리자 자신의 수단을 잃었다면 root가 상태 디렉터리의 기록 파일을 지웁니다. 사용자 이름에 영문자·숫자·`_`·`-` 밖의 문자가 있으면 파일 이름에서는 `%XX`로 바뀌어 있으니 `sudo ls /var/lib/onmaru/security/`로 먼저 확인해 주세요.

  ```sh
  sudo rm /var/lib/onmaru/security/<사용자 이름>.json
  ```

- 기록 파일이 손상되어 읽을 수 없으면 그 사용자의 2차 인증을 없는 것으로 보지 않고 확인을 막습니다. 관리자가 초기화하거나 root가 파일을 지우면 되살아납니다.

### 보안 강화 모드의 설계와 한계

- 확인은 대시보드가 하며 권한 도우미에는 넣지 않았습니다. 도우미의 보안 설계는 그대로입니다.
- 인증 수단 기록은 상태 디렉터리의 `security/<사용자 이름>.json`(디렉터리 `0700`, 파일 `0600`)에 있습니다. 인증 앱의 비밀 키가 들어 있으므로 상태 디렉터리를 백업할 때 함께 보호해 주세요. 복구 코드는 해시만 남깁니다. 패스키로 로그인의 키 조각도 이 기록에 있지만, 혼자서는 아무것도 풀 수 없습니다(아래).
- 비밀번호 재확인은 OMV에 한 번 더 로그인해서 비밀번호를 확인하고, 확인에 쓴 OMV 세션은 바로 끝냅니다. 비밀번호를 틀린 횟수는 로그인 실패 횟수에 합산합니다. 2차 수단을 틀린 횟수에도 같은 기준(브라우저 IP·사용자 이름별로 15분 안에 5번째 실패부터 잠금)을 적용하지만, 로그인 실패와는 따로 집계합니다.
- 확인 성공·실패, 수단 등록·삭제, 패스키로 로그인 켜기·해제·로그인, 정책 변경, 초기화는 `journalctl -u onmaru`에 남습니다. 비밀번호·코드 같은 비밀 값은 남기지 않습니다.
- 패스키로 로그인은 비밀번호를 암호화해 두었다가 패스키 확인 뒤 풀어 평소처럼 OMV에 보냅니다. OMV에는 토큰이나 SSO 같은 비밀번호 없는 로그인이 없고, OMV 세션과 권한 도우미가 비밀번호를 요구하기 때문입니다. 키를 둘로 나눠 비밀번호를 지킵니다.
  - 비밀번호 암호문은 켠 브라우저의 localStorage에만 있고, 대시보드는 인증 수단 기록에 키의 나머지 조각만 둡니다. 복호화 키는 패스키의 PRF 결과와 이 조각을 함께 써야 만들어지며 어디에도 저장하지 않습니다.
  - 대시보드는 패스키 확인(사용자 확인 필수)을 통과한 뒤에만 조각을 내줍니다. 그래서 비밀번호를 풀 때마다 대시보드를 거치고, 로그와 시도 제한이 적용됩니다. 패스키 확인에 실패한 횟수는 2차 수단의 실패 횟수에 합산하고, 풀어 낸 비밀번호가 틀린 횟수는 로그인 실패 횟수에 합산합니다.
  - 등록을 해제하면 조각이 지워지므로 브라우저에 남은 암호문도 쓸 수 없습니다.
  - 패스키로 로그인이 성공할 때마다 조각을 바꿉니다. 브라우저는 새 조각으로 다시 암호화한 항목을 저장한 뒤 로그인을 마치므로, 중간에 응답이 사라져도 지금 조각이나 다음 조각 중 하나로 풀립니다. 두 조각 모두로 풀리지 않는 항목은 회전 전에 복사된 사본으로 보고 그 등록을 지웁니다.
  - 상태 디렉터리나 백업이 새어도 조각만으로는, 브라우저의 항목이 새어도 조각과 패스키 없이는 비밀번호를 풀 수 없습니다.
  - 로그에는 사용자, 브라우저 IP, 패스키 이름, 등록 ID의 앞부분만 남깁니다. 조각·암호문·PRF 결과는 남기지 않습니다.
- 패스키로 로그인에는 다음 한계가 있습니다.
  - 같은 출처의 다른 웹 앱은 브라우저의 localStorage 항목을 읽을 수 있습니다. 예를 들어 OMV와 같은 도메인의 경로 접두사 아래에 대시보드를 두면 OMV 웹 UI도 같은 출처입니다. 조각과 패스키 없이는 풀 수 없지만, 항목까지 떼어 두려면 대시보드에 별도 호스트 이름을 주세요.
  - 사이트 데이터를 지우거나 시크릿 창을 쓰면 브라우저의 항목이 없으므로 다시 켜야 합니다.
  - iCloud 키체인처럼 동기화되는 패스키라도 켠 브라우저에서만 패스키로 로그인할 수 있습니다. 다른 기기에서는 따로 켜 주세요.
  - 패스키(인증기)와 그 잠금(PIN, 생체 인식)을 함께 가진 사람은 등록을 해제하기 전까지 그 브라우저에서 로그인할 수 있고, 그 과정에서 비밀번호가 브라우저에서 풀립니다. 대시보드를 거치므로 로그에는 남습니다. 기기를 잃었다면 다른 브라우저의 보안 페이지에서 그 등록을 해제하거나 패스키를 지워 주세요.
  - PRF 지원은 플랫폼과 패스키 저장소마다 다릅니다. 지원하지 않는 패스키는 2차 인증에만 쓸 수 있습니다.
- 막지 못하는 것도 있습니다.
  - 인증 수단을 아직 등록하지 않은 계정. 첫 수단은 비밀번호만으로 등록할 수 있으므로 비밀번호가 새면 다른 사람이 먼저 등록할 수 있습니다. 2차 인증을 요구할 기능이 있다면 사용자마다 미리 수단을 등록하게 해 주세요(보안 정책 페이지의 "사용자의 로그인 수단"에서 누가 등록했는지 볼 수 있습니다).
  - 대시보드(onmaru) 자체가 뚫린 경우. 확인 값도 대시보드를 거칩니다.
  - OMV 관리자 비밀번호가 새면 OMV 웹 UI로 직접 들어가 root와 같은 일을 할 수 있습니다. 관리자 계정에는 OpenMediaVault의 2차 인증(OMV 8.5 이상)을 함께 쓰는 것을 권합니다.
  - SSH 서버는 원래 LAN에 열려 있으므로, SSH에 직접 접속하는 것은 OMV의 SSH 설정이 정합니다.

## 리버스 프록시

대시보드는 따로 설치한 리버스 프록시 뒤에 둡니다. 아래 예시는 Caddy 기준이며, 다른 프록시를 쓰더라도 "프록시 요구 사항"을 만족하면 됩니다. 대시보드를 둘 호스트와 경로는 프록시 설정에서 정합니다. 별도 서브도메인의 루트에 두어도 되고, 같은 도메인의 경로 접두사(예: `/desk/`) 아래에 두어도 됩니다. 프론트엔드는 상대 경로로 빌드되어 있습니다.

### 수신 방식 고르기

| 프록시 위치 | 수신 방식 | 프록시 대상 |
|---|---|---|
| 이 호스트에서 직접 실행 | 루프백 TCP `127.0.0.1:8090` | `http://127.0.0.1:8090` |
| Docker 컨테이너(bridge 네트워크) | Unix 소켓 `unix:/run/onmaru/onmaru.sock` | 컨테이너에 `/run/onmaru`를 바인드 마운트하고 소켓으로 연결 |
| 그 밖에 꼭 필요한 경우 | `-allow-non-loopback`과 `0.0.0.0:8090` 등 | 해당 주소 |

- 컨테이너 안의 `127.0.0.1`은 컨테이너 자기 자신을 가리키므로 호스트의 루프백에 닿지 않습니다. 그래서 Docker 안의 프록시에는 Unix 소켓을 권장합니다.
- 소켓은 서비스 사용자와 그 기본 그룹(기본값 `onmaru:onmaru`) 소유에 권한 `0660`입니다. root로 실행되는 컨테이너는 접속할 수 있습니다. 비root 사용자로 실행되는 프록시 이미지나 userns-remap 환경에서는 접속할 수 없으니, 프록시 프로세스가 그 그룹 권한을 갖도록 설정해 주세요. 호스트에서 실행하는 프록시라면 프록시 사용자를 서비스 그룹에 추가합니다.
- systemd 유닛은 `RuntimeDirectoryPreserve=yes`로 `/run/onmaru`를 재시작 사이에도 유지합니다. 디렉터리가 새로 만들어지면 컨테이너의 바인드 마운트가 이전 디렉터리를 계속 가리켜 연결이 끊기기 때문입니다.
- **루프백이 아닌 주소에서 수신하는 것은 위험합니다.** 그 주소에 닿을 수 있는 누구나 프록시와 HTTPS를 거치지 않고 접속할 수 있으며, 비밀번호가 평문 HTTP로 전송됩니다. 또한 `X-Forwarded-For`·`X-Forwarded-Proto`를 위조해 로그인 시도 제한을 우회하거나 OMV 인증 로그(fail2ban)에 가짜 IP를 남길 수 있습니다. 이 방식을 사용한다면 방화벽으로 접근을 제한해 주세요.

### 프록시 요구 사항

- `X-Forwarded-Proto`에 브라우저가 접속한 프로토콜(`https` 또는 `http`)을 전달해야 합니다. 백엔드는 이 값이 `https`일 때만 세션 쿠키에 `Secure`를 붙입니다.
- `X-Forwarded-For`의 마지막 항목이 브라우저 IP여야 합니다. 백엔드는 마지막 항목만 로그인 시도 제한과 OMV 인증 로그에 사용합니다. 앞쪽 항목은 브라우저가 임의로 보낼 수 있으므로 쓰지 않습니다.
- 경로 접두사 아래에 둘 때는 접두사를 떼고 전달하고, 끝 슬래시가 없는 주소(`/desk`)를 `/desk/`로 리다이렉트해 주세요. 상대 경로가 `/desk/`를 기준으로 해석되기 때문입니다.
- 백엔드가 보내는 `Cache-Control`과 `ETag`를 바꾸지 말고 그대로 전달해 주세요. 이름에 해시가 붙은 `assets/` 파일은 1년 동안 캐시하고, `index.html`은 매번 다시 확인하게 해서 업그레이드 뒤 새로 고치면 새 파일을 받습니다.
- 웹 터미널은 WebSocket(`/api/terminal`)을 씁니다. 프록시가 WebSocket을 전달해야 하고, `Host` 헤더를 바꾸지 말아야 합니다. 백엔드는 다른 출처에서 연결하지 못하게 `Origin`이 `Host`와 같은지 확인합니다. 백엔드가 30초마다 ping을 보내므로 유휴 연결 제한은 그보다 길어야 합니다.
- 파일 탐색기의 올리기는 파일 하나를 요청 본문 하나로 보냅니다. 프록시에 요청 본문 크기 제한이 있다면 풀거나 올릴 파일보다 크게 맞춰 주세요(nginx는 `client_max_body_size 0`). 큰 파일을 주고받는 동안 본문을 보내거나 받는 데 걸리는 시간에도 제한이 없어야 합니다.
- 파일 탐색기의 복사는 진행 상황을 하나의 응답으로 이어서 보냅니다(`text/event-stream`). 프록시가 응답을 모아 두지 않고 바로 넘겨야 진행 상황이 보입니다. 온마루가 `X-Accel-Buffering: no`를 붙이므로 nginx는 따로 설정하지 않아도 됩니다.
- 응답 대기 시간이 3분보다 길어야 합니다. 서비스 켜기·끄기 같은 조작은 OMV 작업이 끝날 때까지 최대 3분 동안 응답을 기다리며, 프록시가 먼저 연결을 끊으면 작업은 계속 진행되지만 화면에는 시간 초과 오류가 표시됩니다. nginx 계열 프록시는 기본값이 60초이므로 `proxy_read_timeout`을 늘려 주세요.

Caddy의 `reverse_proxy`는 기본 설정으로 이 조건을 모두 만족합니다. `X-Forwarded-Proto`와 `X-Forwarded-For`를 붙이고, `Host`를 그대로 전달하며, WebSocket을 전달하고, 요청 본문 크기와 응답 대기 시간에 제한이 없습니다. Caddy 앞에 다른 프록시가 없다면 `trusted_proxies`는 설정하지 마세요. 그래야 브라우저가 보낸 `X-Forwarded-For`를 Caddy가 덮어씁니다.

### Caddy 예시: OMV 기본 포트를 유지하는 경우

OMV 웹 UI가 설치할 때의 기본값대로 80번 포트(HTTP)를 쓰고 있다면, Caddy는 443번 포트(HTTPS)만 사용하게 합니다. OMV 설정은 바꾸지 않으며, OMV 웹 UI 설정(시스템 → Workbench)의 SSL/TLS는 443번 포트가 겹치지 않도록 꺼 둔 상태(기본값)여야 합니다.

Caddy는 기본적으로 80번 포트에서 HTTP를 HTTPS로 리다이렉트하므로 OMV nginx와 포트가 겹칩니다. 전역 옵션 `auto_https disable_redirects`를 주면 이 리다이렉트를 만들지 않고 80번 포트를 열지 않습니다. 따라서 `http://` 주소로 접속하면 OMV 웹 UI가 응답하고, 대시보드는 반드시 `https://` 주소로 접속해야 합니다. Caddy를 Docker로 실행한다면 443번 포트만 publish합니다.

80번 포트를 쓸 수 없으므로 HTTP-01 방식의 인증서 발급은 할 수 없습니다. 로컬 네트워크에서는 다음 중 하나를 사용합니다.

- `tls internal`: Caddy가 자체 CA로 인증서를 발급합니다. 브라우저 경고를 없애려면 Caddy의 루트 인증서(`<Caddy 데이터 디렉터리>/pki/authorities/local/root.crt`)를 접속하는 기기에 신뢰할 인증서로 등록합니다.
- DNS-01 방식: 실제로 소유한 도메인이 있다면 DNS 공급자 모듈을 포함한 Caddy로 공인 인증서를 받을 수 있습니다. 설정 방법은 Caddy 문서의 `tls` 지시어 `dns` 항목을 참고해 주세요.

서브도메인 루트에 두는 경우:

```caddyfile
{
	auto_https disable_redirects
}

dash.example.lan {
	tls internal
	reverse_proxy 127.0.0.1:8090
}
```

OMV와 같은 이름의 경로 접두사 아래에 두는 경우입니다. `https://nas.example.lan/`은 Caddy를 거쳐 OMV 웹 UI로, `https://nas.example.lan/desk/`는 대시보드로 연결됩니다. 기존 `http://nas.example.lan/`도 그대로 OMV 웹 UI에 접속됩니다.

```caddyfile
{
	auto_https disable_redirects
}

nas.example.lan {
	tls internal
	redir /desk /desk/ 308
	handle_path /desk/* {
		reverse_proxy 127.0.0.1:8090
	}
	handle {
		reverse_proxy 127.0.0.1:80   # OMV 웹 UI(기본 포트)
	}
}
```

두 예시 모두 Caddy가 호스트에서 실행되는 경우입니다. Docker 컨테이너의 Caddy라면 대시보드는 아래의 Unix 소켓 예시처럼 연결하고, OMV 웹 UI 주소는 컨테이너에서 닿는 호스트 주소로 바꿔 주세요.

### Caddy 예시: Caddy를 메인 리버스 프록시로 쓰는 경우

Caddy가 80·443번 포트를 모두 맡아 HTTPS 리다이렉트와 인증서 발급·갱신을 하고, OMV 웹 UI와 온마루를 모두 Caddy 뒤에 두는 구성입니다. 이 경우 OMV 웹 UI 설정(시스템 → Workbench)에서 OMV 포트를 다른 값으로 옮기고 SSL/TLS는 끕니다. 아래 예시에서는 `8001`로 옮겼다고 가정합니다. 온마루의 OMV 주소도 바꾼 포트에 맞춰 `http://127.0.0.1:8001`로 설정해야 합니다(설치 스크립트는 nginx 설정에서 포트를 찾아 제안합니다).

서브도메인 루트에 두고, 프록시가 호스트에서 실행되는 경우:

```caddyfile
dash.example.com {
	reverse_proxy 127.0.0.1:8090
}
```

Docker 컨테이너의 Caddy에서 Unix 소켓으로 연결하는 경우(컨테이너에 `- /run/onmaru:/run/onmaru` 볼륨을 추가해야 합니다):

```caddyfile
dash.example.com {
	reverse_proxy unix//run/onmaru/onmaru.sock
}
```

OMV와 같은 도메인의 경로 접두사 아래에 두는 경우:

```caddyfile
nas.example.com {
	redir /desk /desk/ 308
	handle_path /desk/* {
		reverse_proxy 127.0.0.1:8090
	}
	handle {
		reverse_proxy 127.0.0.1:8001   # OMV 웹 UI(옮긴 포트)
	}
}
```

## 설정 앱

"모든 앱"의 "설정", 작업표시줄 프로필 메뉴의 머리글(사용자 이름), 바탕화면 우클릭 메뉴의 "화면 설정 열기"로 엽니다. 창이 좁으면 왼쪽 메뉴가 숨고 ☰ 단추로 엽니다. 왼쪽 메뉴 맨 위의 사용자 카드를 누르면 프로필이 열립니다.

| 페이지 | 내용 | 권한 |
|---|---|---|
| 프로필 | 프로필 사진(올려서 자르기), 전자 우편과 태그(OMV 사용자 편집 화면의 Tags와 같은 값) 바꾸기, OMV 사용자 편집 화면 열기(관리자) | 모든 사용자 |
| 화면 | 테마(자동·라이트·다크), 바탕화면(기본 배경 또는 올린 이미지), 작업표시줄 아이콘 정렬(가운데·왼쪽) | 모든 사용자 |
| 일반 | 언어(이 브라우저에만 적용)와 애니메이션 | 모든 사용자 |
| 보안 | 이 세션의 확인 수준과 "지금 확인", 패스키·인증 앱·복구 코드 관리, 새 기기에 줄 기기 추가 코드, 패스키로 로그인하는 브라우저(위 "보안 강화 모드") | 모든 사용자 |
| 로그인 화면 | 로그인 배경과 대기 연출 켜기·끄기 | 관리자 |
| 기본 화면 | 화면 설정을 정하지 않은 사용자에게 적용할 기본 테마·바탕화면 | 관리자 |
| 서버 | 워크벤치 주소·SMART 확인 시각·웹 터미널 허용 바꾸기, 권한 도우미 상태와 root 권한 상승, 파일 탐색기의 공유 폴더 목록 받기·디스크 최상위 보기·디스크 휴지통 만들기, 가동 설정 현황과 바꾸는 방법 | 관리자 |
| 보안 정책 | 기능별 보안 강화 단계(웹 터미널, root 권한 상승, 파일 탐색기와 그 확인 범위), 패스키로 로그인의 만료 기간, 패스키 공개 주소 상태, 사용자의 인증 수단 초기화 | 관리자 |
| 업데이트 | 새 버전 확인, 커밋 목록과 새 설정, 대시보드에서 업그레이드(위 "대시보드에서 업그레이드") | 관리자 |
| 정보 | 버전, 라이선스, 오픈 소스 고지 | 모든 사용자 |

- 관리자 페이지는 OMV 관리자 계정에만 보이며, 모든 사용자에게 적용됩니다.
- 배경 이미지는 PNG, JPEG, WebP를 20MB까지 올릴 수 있습니다. 리버스 프록시에 요청 본문 크기 제한이 있다면 20MB 이상으로 맞춰 주세요(nginx의 기본값은 1MB입니다).
- 로그인 배경은 로그인하기 전에 보이는 그림이므로, 대시보드 주소에 접속할 수 있는 누구나 볼 수 있습니다.
- 프로필의 전자 우편과 태그는 OMV 계정 정보입니다. 저장하면 OMV에 "변경 사항 적용" 대기가 생기므로, 관리자 계정은 저장할 때 적용까지 하고(OMV에 미리 적용하지 않은 변경이 있으면 저장하지 않습니다), 일반 사용자 계정은 관리자가 OMV 웹 UI에서 적용해야 합니다. OMV 기본 관리자 계정(`admin`)처럼 시스템 계정이거나 OMV에서 수정을 막은 계정은 바꿀 수 없습니다. 비밀번호·그룹 등 나머지 계정 정보는 OMV 웹 UI에서 바꿔 주세요.
- 그 밖의 OMV와 운영체제 설정은 설정 앱에서 다루지 않습니다. OMV 웹 UI에서 바꿔 주세요.

## 개발

기여 방법(개발 환경, 브랜치와 풀 리퀘스트, 번역)은 [CONTRIBUTING.md](CONTRIBUTING.md)(영어)와 [CONTRIBUTING.ko.md](CONTRIBUTING.ko.md)에 있습니다. 개발 명령과 설계 문서는 `CLAUDE.md`와 `.claude/` 디렉터리에 있습니다. `make dev-fake`를 실행하면 가짜 OMV에 연결된 개발 서버가 뜹니다.

개발 도구는 "빌드 및 설치"의 빌드 도구와 같습니다. 다만 테스트(`make test`, `make check`)에 쓰는 Vitest 5는 Node.js 22.12 이상을 공식 지원합니다. Debian 13의 Node.js 20.19에서도 테스트가 통과하지만 지원 범위 밖입니다.
