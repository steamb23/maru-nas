# <img src="frontend/src/assets/logo/onmaru-lockup.svg" alt="온마루 (Onmaru)" height="80">

> A suspiciously normal desktop-like dashboard for openmediavault.

OpenMediaVault 8 위에 올리는 데스크톱형 웹 대시보드입니다. 창·작업표시줄·바탕화면 위젯으로 NAS 가동 현황을 확인하고, 컨테이너와 핵심 서비스를 간단히 켜고 끌 수 있습니다. 심층 설정은 OMV 기본 웹 UI에서 합니다.

- 로컬 네트워크 전용입니다. 인터넷에 노출하는 구성을 전제로 하지 않으며, 인터넷에 노출되었을 때 어떤 보안 취약점이 드러날지 충분히 검증되지 않았습니다.
- 로그인은 OMV 계정으로 합니다. 백엔드가 OMV `rpc.php`에 로그인을 위임하며, 설정 변경도 로그인한 사용자의 OMV 세션으로만 합니다.
- Go 실행 파일 하나(프론트엔드 포함)를 systemd 서비스로 실행하고, 앞단의 리버스 프록시가 HTTPS를 맡습니다.

## 빌드 및 설치

### 준비

OpenMediaVault 8의 모든 버전(8.0 이상)에서 동작합니다. 버전에 따라 다음이 다릅니다.

- 2단계 인증은 OMV 8.5 이상에서만 쓸 수 있습니다. OMV 8.5에서 생긴 기능이기 때문입니다.
- OMV 8.0·8.1은 자동 로그아웃 시간을 알려 주지 않습니다. 그래서 대시보드에 세션의 남은 시간이 표시되지 않고, OMV 세션이 끝난 것은 대시보드가 주기적으로 OMV에 확인할 때 알게 됩니다.

OMV 설치 이미지(ISO)로 막 설치했다면 이미지의 버전이 그대로 설치됩니다(예: 8.3.1 이미지는 OMV 8.3.1). 보안 업데이트도 받을 수 있게 OMV 웹 UI의 시스템 → 업데이트 관리에서 업데이트하거나 `sudo omv-upgrade`를 실행해 두기를 권장합니다. 지금 버전은 `dpkg-query -W openmediavault`로 확인합니다.

빌드에는 아래 도구가 필요합니다. OMV 설치 이미지로 설치한 직후에는 어느 것도 들어 있지 않지만, 모두 OMV 8(Debian 13)이 기본으로 쓰는 apt 저장소에서 설치할 수 있습니다.

| 도구 | 필요한 버전 | apt 패키지(버전) | 비고 |
|---|---|---|---|
| Go | 1.27.1 이상 | `golang-go`(trixie-backports 1.27, 기본 저장소 1.24) | `backend/go.mod` 기준입니다. |
| Node.js | 20.19 이상 또는 22.12 이상 | `nodejs`(20.19) | Vite 8 기준입니다. |
| npm | 7 이상 | `npm`(9.2) | Debian에서는 `nodejs`와 따로 설치합니다. |
| make | GNU make | `make`(4.4) | |
| git | | `git`(2.47) | 소스와 아이콘 서브모듈을 받고, 빌드할 때 커밋 정보를 실행 파일에 넣습니다. |

```sh
sudo apt install git make nodejs npm curl
sudo apt install -t trixie-backports golang-go
```

- OMV는 커널 업데이트용으로 Debian의 trixie-backports 저장소를 기본으로 켜 둡니다. 두 번째 줄은 그 저장소에서 Go 1.27을 설치합니다.
- `-t trixie-backports` 없이 설치하면 Go 1.24가 설치됩니다. 이때는 첫 빌드에서 Go가 1.27.1 툴체인을 proxy.golang.org에서 자동으로 내려받습니다(약 75MB). 내려받은 파일과 푼 툴체인을 합쳐 `~/go/pkg/mod`에 약 330MB가 생깁니다. `GOTOOLCHAIN=local`로 설정했거나 proxy.golang.org에 접속할 수 없다면 backports나 [go.dev/dl](https://go.dev/dl/)의 배포본을 설치해 주세요.
- `curl`은 선택입니다. 없으면 설치 끝의 상태 확인을 건너뜁니다. C 컴파일러는 필요하지 않습니다.
- Node.js 20에서는 `npm ci`가 Vitest의 `EBADENGINE` 경고를 표시합니다. 개발용 테스트 도구에 대한 경고이므로 빌드에는 영향이 없습니다.
- root 계정이라면 `sudo` 없이 실행합니다.
- 빌드하는 동안 github.com(아이콘 서브모듈)과 registry.npmjs.org(npm 의존성)에 접속하며, 도구 설치와 빌드에 약 1.1GB의 여유 공간이 필요합니다(backports의 Go 기준. 기본 저장소의 Go 1.24를 쓰면 툴체인 때문에 약 0.3GB가 더 필요합니다).

소스는 git으로 받습니다. `stable` 브랜치가 최신 릴리스이고 `main`은 개발 중인 코드이므로 설치에는 `stable`을 받습니다. 아이콘 서브모듈은 설치 스크립트가 받으므로 `--recurse-submodules`는 필요 없습니다.

```sh
git clone -b stable https://github.com/steamb23/Onmaru.git
cd Onmaru
```

특정 버전을 설치하려면 클론한 뒤 그 버전의 태그를 체크아웃합니다(예: `git checkout v0.10.0`). 릴리스 목록과 변경 내용은 [Releases](https://github.com/steamb23/Onmaru/releases)에 있습니다.

### 설치 스크립트

```sh
./install.sh
```

일반 사용자 계정이라면 **sudo 없이** 실행해 주세요. 인터랙티브 설치 스크립트이며 다음 순서로 진행됩니다.

1. **설정 입력**: 서비스 사용자, 수신 방식, OMV 주소, SMART 갱신 시각, OMV 워크벤치 주소, 권한 도우미 설치 여부를 묻고 요약을 보여 준 뒤 확인을 받습니다. 입력은 이 단계에서 모두 끝납니다.
2. **빌드**: 실행한 계정으로 빌드합니다. 처음 클론한 상태라면 아이콘 서브모듈과 npm 의존성부터 준비합니다(`make build` → `bin/onmaru`, `bin/onmaru-helper`).
3. **설치**: root 권한이 필요한 단계입니다. 일반 사용자라면 스크립트가 1단계의 설정을 옵션으로 넘겨 스스로 `sudo ./install.sh --service-install ...`을 실행하므로 비밀번호만 한 번 입력하면 됩니다. root 계정만 있는 환경이라면 sudo 없이 그대로 이어서 진행합니다.

OMV 설치 이미지가 만든 일반 사용자는 sudo 그룹에 들어 있으므로 이 방식으로 설치할 수 있습니다. 다만 OMV는 root와 `_ssh` 그룹 사용자에게만 SSH 접속을 허용하므로, 그 계정으로 SSH에 접속하려면 OMV 웹 UI의 사용자 편집 화면에서 `_ssh` 그룹을 더해 주세요.

설치 단계에서는 다음 작업을 합니다.

- 시스템 사용자를 만들고(기본값 `onmaru`), `bin/onmaru`를 `/usr/local/bin/onmaru`에 설치합니다.
- 설정 파일 `/etc/default/onmaru`와 systemd 유닛 `/etc/systemd/system/onmaru.service`를 작성한 뒤 서비스를 시작합니다.
- 사용자 설정(위젯 배치, 바탕화면 바로가기, 화면 설정 등), 관리자의 전역 설정, 올린 배경 이미지는 `/var/lib/onmaru`(`StateDirectory=`)에 저장됩니다.
- 권한 도우미(기본값 설치)는 `/usr/local/bin/onmaru-helper`, `/etc/default/onmaru-helper`, `/etc/systemd/system/onmaru-helper.socket`·`.service`를 작성하고 소켓을 켭니다. 설치하지 않기로 하면 이전에 설치한 도우미를 지웁니다(아래 "권한 도우미" 참고).

다시 실행하면 기존 설정을 기본값으로 보여 주며, 업그레이드할 때도 같은 명령을 사용합니다. 설정을 바꾸지 않고 업그레이드만 하려면 `./install.sh --upgrade`를 사용합니다(아래 "업그레이드" 참고). 설정이 바뀌면 기존 `/etc/default/onmaru`는 `/etc/default/onmaru.bak-<시각>`으로 백업됩니다. 안내 문구는 로캘에 따라 영어 또는 한국어로 표시되며, `--lang en|ko`로 직접 고를 수도 있습니다.

| 옵션 | 설명 |
|---|---|
| (없음) | 빌드한 뒤 설치하거나 업그레이드합니다. |
| `--upgrade` | 기존 설치의 설정 그대로 묻지 않고 빌드한 뒤 업그레이드합니다. 기존 설치에 없는 설정(새 버전에서 생긴 설정)만 묻습니다. |
| `--no-build` | 빌드를 건너뛰고 기존 `bin/onmaru`(권한 도우미를 설치하면 `bin/onmaru-helper`도)를 설치합니다. |
| `--uninstall` | 서비스, 실행 파일, 설정을 제거합니다. |
| `--service-install` | 빌드 없이 설치 단계만 실행합니다(root 전용). 아래 설정 옵션을 모두 주면 묻지 않고 설치합니다. |
| `--lang en\|ko` | 안내 문구 언어를 고릅니다. |
| `--user NAME` | 서비스 사용자입니다(기본값 `onmaru`). |
| `--listen ADDR` | 수신 주소입니다. `127.0.0.1:8090`, `unix:/run/onmaru/onmaru.sock`, 또는 `host:port`를 지정합니다. |
| `--allow-non-loopback` | 루프백이 아닌 `--listen` 주소를 허용합니다(위험). |
| `--omv-url URL` | OMV 웹 UI 주소입니다(루프백). |
| `--smart-refresh-at HH:MM` | SMART 정보를 매일 다시 가져올 시각입니다. |
| `--workbench-url URL` | 브라우저에서 OMV 웹 UI를 열 주소입니다. 빈 값(`--workbench-url ''`)이면 "OMV 워크벤치" 앱을 숨깁니다. 질문에서는 `-`를 입력하면 끕니다. |
| `--helper`, `--no-helper` | 권한 도우미(root로 도는 `onmaru-helper`)를 설치하거나 설치하지 않습니다. 질문의 기본값은 설치입니다. `--no-helper`는 이미 설치된 도우미를 지웁니다. |
| `--elevate-group GROUP` | root 권한 상승에 `openmediavault-admin`과 함께 필요한 그룹입니다(기본값 `sudo`). `--helper`일 때만 씁니다. |

설정 옵션으로 준 항목은 묻지 않습니다. 옵션 없이 실행할 때는 설정을 모두 주더라도 요약을 보여 주고 진행 여부를 확인합니다. 확인까지 생략하는 것은 root로 `--service-install`에 설정을 모두 준 경우뿐이므로, 자동화에는 다음과 같이 사용합니다(빌드는 미리 해 두어야 합니다).

```sh
./install.sh --service-install --user onmaru --listen unix:/run/onmaru/onmaru.sock \
  --omv-url http://127.0.0.1 --smart-refresh-at 00:00 --workbench-url https://nas.example.lan/ --no-helper
```

root로 실행했는데 저장소의 소유자가 root가 아니면(`sudo ./install.sh`, `sudo -i`, `su` 등) 빌드를 건너뜁니다. root로 빌드하면 저장소에 root 소유 파일이 생기고, sudo 환경의 PATH에는 사용자가 설치한 Go·npm이 없을 수 있기 때문입니다. 이때는 기존 `bin/onmaru`로 설치만 할지 물어봅니다(`--upgrade`이면 묻지 않고 멈춥니다).

### 업그레이드

```sh
git pull
./install.sh --upgrade
```

`stable`을 받았다면 `git pull`로 최신 릴리스가 내려옵니다. 태그를 체크아웃해 특정 버전을 쓰고 있다면 `git pull` 대신 `git fetch --tags`로 받고 새 버전의 태그를 체크아웃합니다.

`--upgrade`는 지금 설치된 설정(`/etc/systemd/system/onmaru.service`의 서비스 사용자, `/etc/default/onmaru`의 나머지 설정)을 그대로 써서 빌드하고 설치합니다. 설정 질문, 요약 확인, 포트 사용 중·OMV의 Force SSL/TLS 같은 경고의 확인을 모두 건너뛰므로(경고는 표시합니다) 일반 사용자라면 sudo 비밀번호만 입력하면 됩니다.

- 새 버전에서 설정이 추가되어 기존 설치에 그 값이 없으면 그 설정만 묻습니다.
- 설정 옵션(`--listen` 등)을 함께 주면 그 항목만 기존 값 대신 씁니다.
- 수신 주소와 서비스 사용자가 그대로면 리버스 프록시 설정도 그대로 맞으므로, 끝난 뒤 리버스 프록시 안내 없이 로그 위치만 알립니다.
- 권한 도우미가 생기기 전 버전에서 올라오면 도우미 설치 여부를 묻습니다. 설치되어 있다면 도우미도 새 실행 파일로 다시 시작합니다(대시보드도 다시 시작하므로 어차피 모두 다시 로그인합니다).
- 기존 설치가 없거나, 기존 설정이 새 버전의 검사를 통과하지 못하면 멈춥니다. 이때는 `--upgrade` 없이 실행해 설정을 다시 입력합니다.

개발 서버(`make dev`)의 백엔드도 기본으로 `127.0.0.1:8090`을 사용합니다. 같은 머신에서 개발한다면 서비스는 Unix 소켓이나 다른 포트로 설치해 주세요. 설치 스크립트는 포트가 이미 사용 중이면 경고합니다.

제거하려면 `./install.sh --uninstall`을 실행합니다. 권한 도우미를 설치했다면 함께 지웁니다. `/var/lib/onmaru`와 서비스 사용자는 확인을 받은 뒤에만 삭제합니다. 제거하면 `/run/onmaru`도 지워지므로, 컨테이너 프록시에 이 디렉터리를 마운트해 두었다면 다시 설치한 뒤 프록시 컨테이너를 다시 만들어야 합니다.

리버스 프록시는 설치 스크립트가 설정하지 않습니다. 아래 "리버스 프록시" 항목을 참고해 주세요.

## 설정

`/etc/default/onmaru`의 환경 변수나 명령줄 플래그로 설정합니다. 값을 바꾼 뒤에는 `sudo systemctl restart onmaru`로 다시 시작해 주세요. 지금 쓰는 값과 그 출처(기본값, 환경 변수, 명령줄 플래그)는 관리자가 설정 앱의 "서버" 페이지에서 볼 수 있습니다.

워크벤치 주소(`-workbench-url`), SMART 확인 시각(`-smart-refresh-at`), 웹 터미널 허용(`-terminal`)은 설정 앱의 "서버" 페이지에서 바꿀 수도 있습니다. 여기서 바꾼 값은 상태 디렉터리의 `site.json`에 저장되어 플래그·환경 변수보다 우선하며, 다시 시작하지 않아도 바로 적용됩니다. `install.sh`로 다시 설치하거나 업그레이드해도 그대로 남으므로, 플래그 값으로 돌아가려면 그 페이지에서 "서버 값 사용"을 눌러 주세요.

| 플래그 | 환경 변수 | 기본값 | 설명 |
|---|---|---|---|
| `-listen` | `ONMARU_LISTEN` | `127.0.0.1:8090` | 수신 주소입니다. 루프백 `host:port` 또는 `unix:/절대/경로.sock`(Unix 소켓, 권한 `0660`)을 지정합니다. |
| `-allow-non-loopback` | `ONMARU_ALLOW_NON_LOOPBACK` | `false` | 루프백이 아닌 TCP 주소(`0.0.0.0:8090` 등)도 허용합니다. 위험하니 아래 설명을 먼저 읽어 주세요. |
| `-omv-url` | `ONMARU_OMV_URL` | `http://127.0.0.1` | OMV 웹 UI(nginx) 주소입니다. 백엔드가 `<주소>/rpc.php`로 로그인을 위임합니다. 루프백 주소만 허용합니다. OMV 웹 UI 포트를 바꿨다면 포트까지 적어 주세요(설치 스크립트는 nginx 설정에서 포트를 찾아 제안합니다). 백엔드는 평문 HTTP로만 접속하므로 OMV의 "Force SSL/TLS"는 꺼져 있어야 합니다. |
| `-cookie-path` | `ONMARU_COOKIE_PATH` | `/` | 브라우저가 보는 대시보드 경로(세션 쿠키의 Path)입니다. 경로 접두사 아래에 둘 때 좁힐 수 있습니다. |
| `-state-dir` | `ONMARU_STATE_DIR`, `STATE_DIRECTORY` | (없음) | 대시보드 설정을 저장할 디렉터리입니다(사용자 설정 `users/<사용자 이름>.json`, 전역 설정 `site.json`, 배경 이미지 `images/`). 비워 두면 메모리에만 보관하므로 재시작하면 사라집니다. systemd의 `StateDirectory=`가 `STATE_DIRECTORY`를 넘겨줍니다. |
| `-smart-refresh-at` | `ONMARU_SMART_REFRESH_AT` | `00:00` | SMART 정보를 하루 한 번 다시 가져오는 기준 시각입니다(`HH:MM`, 서버 로컬 시간). 마지막 조회가 이 시각 이전이면 다음 접속 때 다시 가져옵니다. SMART 조회는 대기 중인 디스크를 깨우므로 자동 주기 조회는 하지 않습니다. |
| `-workbench-url` | `ONMARU_WORKBENCH_URL` | (없음) | 브라우저에서 OMV 웹 UI(workbench)를 열 주소입니다. 아래 "OMV 워크벤치 열기"를 참고해 주세요. 비워 두면 "OMV 워크벤치" 앱과 프로필 메뉴 항목이 보이지 않습니다. |
| `-helper-socket` | `ONMARU_HELPER_SOCKET` | (없음) | 권한 도우미 소켓의 절대 경로입니다(설치 스크립트는 `/run/onmaru-helper/helper.sock`). 비워 두면 도우미를 쓰는 기능이 꺼집니다. 아래 "권한 도우미"를 참고해 주세요. |
| `-terminal` | `ONMARU_TERMINAL` | `false` | 웹 터미널을 허용합니다. 설정 앱의 "서버" 페이지에서도 켜고 끌 수 있습니다. 아래 "웹 터미널"을 참고해 주세요. |
| `-ssh-addr` | `ONMARU_SSH_ADDR` | `auto` | 웹 터미널이 접속할 SSH 서버 주소입니다. `auto`는 `/etc/ssh/sshd_config`의 `Port`로 `127.0.0.1`에 접속하므로 OMV에서 포트를 바꿔도 따라갑니다. 직접 적을 때는 루프백 `IP:포트`만 받습니다. |
| `-ssh-host-keys` | `ONMARU_SSH_HOST_KEYS` | `/etc/ssh/ssh_host_*_key.pub` | 웹 터미널이 받아들일 SSH 서버 호스트 공개 키 파일의 glob 패턴입니다. 서버 키가 이 중 하나와 같을 때만 접속합니다. 보통은 바꾸지 않습니다. |

세션은 백엔드 메모리에만 있으므로 백엔드를 재시작하면 모든 사용자가 다시 로그인해야 합니다. `/var/lib/onmaru`에는 대시보드 자신의 상태만 들어 있으며 OMV 설정과는 관계가 없습니다. 백업할 때 이 디렉터리를 함께 복사하면 사용자 설정, 전역 설정, 올린 배경 이미지가 유지됩니다.

### OMV 워크벤치 열기

`-workbench-url`을 설정하면 "모든 앱"·바탕화면 바로가기의 "OMV 워크벤치"와 프로필 메뉴의 "OMV 워크벤치 열기"가 OMV 웹 UI를 브라우저의 새 탭으로 엽니다.

- 값은 브라우저에서 OMV에 접속하는 주소입니다(예: `https://nas.example.lan/`). `http://`·`https://`로 시작하는 주소 또는 대시보드 기준 경로(`/`, `./`, `../`)를 받습니다. 대시보드를 OMV와 같은 호스트의 경로 접두사(예: `/desk/`) 아래에 두었다면 `/`도 됩니다. 쿼리·프래그먼트는 받지 않으며, `nas.example.lan/`처럼 `http(s)://`가 없는 주소는 거부합니다.
- 같은 탭을 다시 씁니다. 이미 연 OMV 탭이 있으면 새 탭을 만들지 않고 그 탭에서 OMV 첫 화면으로 이동합니다.
- OMV 로그인은 그 탭에서 따로 합니다. OMV는 탭마다 로그인 상태를 따로 두고 비밀번호 없이 로그인하는 방법을 제공하지 않으므로, 대시보드 로그인을 OMV 탭에 넘길 수 없습니다. 탭을 닫지 않고 다시 쓰는 동안에는 로그인이 유지됩니다. 처음 로그인하는 브라우저라면 OMV가 "새 브라우저 로그인" 알림 메일을 보낼 수 있습니다.
- 대시보드 안의 창(iframe)으로 띄우지 않는 이유: OMV 웹 UI는 `X-Frame-Options: SAMEORIGIN`을 보내므로 대시보드와 출처(호스트·포트)가 같을 때만 iframe에 들어갈 수 있습니다. 보안 헤더를 끄는 방식은 쓰지 않습니다.

## 권한 도우미

권한 도우미(`onmaru-helper`)는 root로 도는 별도 서비스입니다. 대시보드 자신은 권한이 없는 전용 사용자로 돌고 권한을 올릴 수 없으므로(`NoNewPrivileges=yes`), 다음 일은 도우미를 거칩니다.

- **사용자 권한 연산**: 로그인한 사용자 자신의 Linux 계정(uid, 기본 그룹, 보조 그룹)으로 파일을 읽고 씁니다. 실제로 열 수 있는지는 커널이 소유권과 ACL로 판단하므로 SMB로 접속할 때와 같은 권한이 적용됩니다. 대상은 그 사용자의 홈 디렉터리와 `/srv` 아래에 마운트된 데이터 파일시스템뿐입니다. 파일 탐색기 같은 기능이 이것을 쓰고, 웹 터미널의 일회용 SSH 키(아래 "웹 터미널")도 이 권한으로 넣고 지웁니다.
- **root 권한 연산**: 관리자가 비밀번호를 다시 입력하면 그 대시보드 세션에서 5분 동안 정해진 root 연산을 쓸 수 있습니다(sudo와 비슷합니다). 임의의 명령을 실행하는 기능은 없고, 기능마다 필요한 연산만 따로 만들어 둡니다. 지금은 실행 권한 확인(`id`)만 있습니다.

설치 스크립트가 기본으로 설치합니다. 질문에서 설치하지 않기로 하거나 `--no-helper`를 주면 설치하지 않으며, 이때 도우미가 필요한 기능은 쓸 수 없지만 나머지 기능은 그대로 쓸 수 있습니다. 설치 상태와 지금 세션의 실행 권한, 권한 상승은 관리자가 설정 앱의 "서버" 페이지에서 확인할 수 있습니다.

### 보안 설계

도우미는 대시보드의 말을 그대로 믿지 않습니다. 대시보드가 뚫려도 곧바로 root나 모든 사용자의 권한이 되지 않게 하기 위해서입니다.

- 소켓(`/run/onmaru-helper/helper.sock`, 권한 `0600`)에는 대시보드 서비스 사용자만 접속할 수 있고, 도우미가 접속한 프로세스의 uid(`SO_PEERCRED`)를 다시 확인합니다. Docker 프록시에 마운트하는 `/run/onmaru`와는 다른 디렉터리입니다.
- 로그인할 때 대시보드가 받은 비밀번호를 도우미가 `unix_chkpwd`로 직접 확인한 뒤에만 그 세션에 티켓을 발급합니다. 티켓은 도우미 메모리에만 있으며, 로그아웃·세션 만료 때 폐기되고 도우미나 대시보드가 다시 시작하면 모두 사라집니다. 2단계 인증을 쓰는 계정은 인증을 마친 뒤에야 티켓을 쓸 수 있습니다.
- 티켓을 주는 계정은 OMV 로그인과 같은 기준입니다. root는 받지 않고, `openmediavault-admin` 그룹이거나 일반 사용자 uid 범위(`/etc/login.defs`의 `UID_MIN`~`UID_MAX`)여야 합니다.
- root 권한 상승은 `openmediavault-admin`과 상승 그룹(기본값 `sudo`, 설치할 때 `--elevate-group`으로 바꿈) 모두에 속한 사용자만, 비밀번호를 다시 입력해야 할 수 있습니다. 상승은 그 세션에만 붙고 5분 뒤 끝나며(연산을 해도 늘어나지 않습니다), 서버 페이지에서 바로 끝낼 수 있습니다. 상승 그룹을 `openmediavault-admin`으로 정하면 OMV 관리자는 모두 상승할 수 있습니다.
- 비밀번호 확인은 사용자마다 5분 안에 3번 틀리면 30초부터 두 배씩 최대 15분 동안 잠깁니다. `unix_chkpwd`는 PAM의 실패 잠금(`pam_faillock`)을 거치지 않으므로 이 잠금으로 계정이 영구히 잠기지는 않습니다.
- 연산은 매번 자식 프로세스로 실행하며, 사용자 권한 연산은 시작하기 전에 그 사용자로 권한을 내립니다. root 프로세스는 파일 내용을 다루지 않습니다.
- systemd 유닛은 root여도 권한을 좁혀 둡니다. 사용자 권한으로 내리고 자기 자식 프로세스를 멈추는 권한(`CAP_SETUID`, `CAP_SETGID`, `CAP_KILL`)만 남기고, 네트워크를 쓰지 않으며(`PrivateNetwork=yes`), 파일시스템은 `/srv`와 `/home` 말고는 읽기 전용입니다.
- 비밀번호와 티켓은 기록하지 않습니다. 도우미는 비밀번호 확인 결과, 모든 root 연산, 파일 쓰기 연산(경로 포함)을 `journalctl -u onmaru-helper`에 남깁니다. 파일 읽기는 경로 없이 연산과 결과만 남깁니다.

남는 위험도 있습니다. 대시보드가 뚫리면 공격자는 그때 로그인해 있는 사용자의 티켓을 쓸 수 있고, 그 뒤에 입력되는 비밀번호를 가로챌 수 있습니다. OMV 관리자는 원래 OMV 웹 UI로 root와 같은 일을 할 수 있으므로, 도우미의 root 권한 상승이 관리자에게 새로운 권한을 주지는 않습니다.

### 제한

- 계정은 로컬 `/etc/passwd`·`/etc/group`과 `/etc/shadow`(`unix_chkpwd`)로만 확인합니다. LDAP 플러그인 등으로 들어오는 계정은 대시보드에는 로그인할 수 있지만 도우미 티켓은 받지 못합니다.
- 홈 디렉터리가 `/home`이나 `/srv` 아래가 아니면 읽기만 할 수 있습니다(유닛의 `ReadWritePaths=`).

### 설치 확인

```sh
systemctl status onmaru-helper.socket
```

로그인한 뒤 설정 앱의 "서버" 페이지에서 "실행 권한"이 내 계정의 uid로 나오는지, 권한 상승 뒤 "실행 권한(root)"이 uid 0으로 나오는지 확인합니다. 도우미가 받은 요청과 결과는 다음 명령으로 봅니다.

```sh
journalctl -u onmaru-helper -e
```

도우미 유닛의 보안 설정은 `systemd-analyze security onmaru-helper`로 점검할 수 있습니다.

## 웹 터미널

"모든 앱"의 "터미널"은 대시보드에 로그인한 계정으로 이 NAS의 SSH 서버(sshd)에 접속한 셸을 창 안에 엽니다. 대시보드가 같은 호스트의 SSH 서버(`127.0.0.1`)에 SSH로 접속해 화면을 중계하므로, 누가 어떤 방법으로 들어갈 수 있는지는 OMV의 SSH 설정이 그대로 정합니다.

- 기본으로 꺼져 있습니다. 관리자가 설정 앱의 "서버" 페이지에서 "웹 터미널"을 켜거나 `ONMARU_TERMINAL=true`로 켭니다. 끄면 열려 있던 터미널도 바로 닫힙니다.
- OMV에서 SSH 서비스가 켜져 있어야 하고, 계정이 SSH 로그인을 허용한 그룹(OMV 기본값 `_ssh`)에 있어야 합니다. 그룹은 OMV 웹 UI의 사용자 편집 화면에서 더할 수 있습니다. OMV 기본 관리자 계정(`admin`)은 셸이 없어 쓸 수 없습니다. 다른 계정이나 root로 접속하는 기능은 없으며, root 작업은 셸 안에서 `sudo`로 합니다.
- 인증
  - 권한 도우미가 있으면 비밀번호를 다시 묻지 않습니다. 접속할 때마다 대시보드가 메모리에서 일회용 키를 만들고, 도우미가 사용자 권한으로 `~/.ssh/authorized_keys`에 그 키를 2분 동안 이 호스트 안의 접속에만 쓸 수 있는 줄(`restrict,pty,from="127.0.0.1,::1",expiry-time=…`, 주석 `onmaru-ephemeral`)로 넣었다가 인증이 끝나면 바로 지웁니다. 공개 키만 받는 SSH 설정(OMV의 "Password authentication" 끔)에서도 됩니다.
  - 도우미가 없거나 키를 쓸 수 없으면 SSH 서버가 묻는 비밀번호(와 2단계 인증 코드)를 터미널 안에서 입력합니다. 비밀번호는 저장하지 않고 SSH 서버로 바로 넘깁니다.
  - 홈 디렉터리에 그룹이나 다른 사용자의 쓰기 권한이 있으면 SSH 서버(`StrictModes`)가 그 안의 키를 무시하므로 일회용 키를 쓸 수 없습니다. 그 권한을 빼거나(`chmod go-w <홈 디렉터리>`) 비밀번호로 접속해 주세요.
- 도우미 없이 공개 키만 받는 SSH 서버를 쓴다면, 이 호스트 안의 접속에만 비밀번호를 허용할 수 있습니다. OMV 웹 UI의 SSH 설정 "추가 옵션"에 다음을 넣습니다. 추가 옵션은 `Include /etc/ssh/sshd_config.d/*.conf` 바로 앞에 들어가므로, 마지막 `Match all`이 없으면 그 뒤의 `Include`까지 이 조건 안에 들어갑니다.

  ```
  Match Address 127.0.0.1,::1
      PasswordAuthentication yes
  Match all
  ```

- 한 대시보드 세션(로그인한 브라우저)은 SSH 연결 하나를 함께 쓰므로, 다른 탭에서 터미널을 열 때는 다시 묻지 않습니다. 창을 닫거나, 로그아웃하거나, 세션이 만료되면 셸이 끝납니다. 터미널에 입력하는 동안에는 세션이 연장되지만 출력만 나오는 동안에는 연장되지 않으므로, 오래 걸리는 작업은 `tmux`나 `screen` 안에서 실행해 주세요.
- 복사는 Ctrl+Shift+C, 붙여 넣기는 Ctrl+Shift+V입니다.

### 웹 터미널의 보안

- 대시보드는 SSH 서버의 클라이언트일 뿐입니다. SSH 서버는 원래 LAN에 열려 있으므로 대시보드가 뚫려도 새로 얻는 권한은 없고, 로그인 기록·PAM 세션·`AllowGroups` 같은 SSH 정책도 그대로 적용됩니다. 호스트 키는 `/etc/ssh/ssh_host_*_key.pub`와 비교해 같은 서버에만 접속합니다.
- 일회용 키는 도우미의 기존 파일 쓰기 권한(로그인한 사용자 자신의 홈) 안의 일이라 새 권한을 더하지 않습니다. 도우미는 키 줄을 직접 만들고(옵션을 대시보드가 정할 수 없습니다) ed25519 공개 키만 받으며, `journalctl -u onmaru-helper`에는 키 지문만 남깁니다. 지우지 못한 줄도 2분 뒤에는 SSH 서버가 받지 않고 다음 접속 때 지워집니다.
- SSH 서버와 fail2ban에는 접속지가 `127.0.0.1`로만 보입니다. 그래서 대시보드가 웹 터미널의 비밀번호 실패를 브라우저 IP·사용자 이름별로 따로 세어 잠급니다(로그인과 같은 기준). 대시보드 로그(`journalctl -u onmaru`)에는 사용자, 브라우저 IP, 결과만 남습니다.

## 리버스 프록시

대시보드는 따로 설치한 리버스 프록시 뒤에 둡니다. 아래 예시는 Caddy 기준이며, 다른 프록시를 쓰더라도 "프록시 요구 사항"을 만족하면 됩니다. 대시보드를 둘 호스트와 경로는 프록시 설정에서 정합니다. 별도 서브도메인의 루트에 두어도 되고, 같은 도메인의 경로 접두사(예: `/desk/`) 아래에 두어도 됩니다. 프론트엔드는 상대 경로로 빌드되어 있습니다.

### 수신 방식 고르기

| 프록시 위치 | 수신 방식 | 프록시 대상 |
|---|---|---|
| 이 호스트에서 직접 실행 | 루프백 TCP `127.0.0.1:8090` | `http://127.0.0.1:8090` |
| Docker 컨테이너(bridge 네트워크) | Unix 소켓 `unix:/run/onmaru/onmaru.sock` | 컨테이너에 `/run/onmaru`를 바인드 마운트하고 소켓으로 연결 |
| 그 밖에 꼭 필요한 경우 | `-allow-non-loopback`과 `0.0.0.0:8090` 등 | 해당 주소 |

- 컨테이너 안의 `127.0.0.1`은 컨테이너 자기 자신을 가리키므로 호스트의 루프백에 닿지 않습니다. 그래서 Docker 안의 프록시에는 Unix 소켓을 권장합니다.
- 소켓은 서비스 사용자와 그 기본 그룹(기본값 `onmaru:onmaru`) 소유에 권한 `0660`입니다. root로 실행되는 컨테이너는 접속할 수 있습니다. 비root 사용자로 실행되는 프록시 이미지나 userns-remap 환경에서는 접속할 수 없으니, 프록시 프로세스가 그 그룹 권한을 갖도록 설정해 주세요. 호스트에서 실행하는 프록시라면 프록시 사용자를 서비스 그룹에 추가합니다.
- systemd 유닛은 `RuntimeDirectoryPreserve=yes`로 `/run/onmaru`를 재시작 사이에도 유지합니다. 디렉터리가 새로 만들어지면 컨테이너의 바인드 마운트가 이전 디렉터리를 계속 가리켜 연결이 끊기기 때문입니다.
- **루프백이 아닌 주소에서 수신하는 것은 위험합니다.** 그 주소에 닿을 수 있는 누구나 프록시와 HTTPS를 거치지 않고 접속할 수 있으며, 비밀번호가 평문 HTTP로 전송됩니다. 또한 `X-Forwarded-For`·`X-Forwarded-Proto`를 위조해 로그인 시도 제한을 우회하거나 OMV 인증 로그(fail2ban)에 가짜 IP를 남길 수 있습니다. 이 방식을 사용한다면 방화벽으로 접근을 제한해 주세요.

### 프록시 요구 사항

- `X-Forwarded-Proto`에 브라우저가 접속한 프로토콜(`https` 또는 `http`)을 전달해야 합니다. 백엔드는 이 값이 `https`일 때만 세션 쿠키에 `Secure`를 붙입니다.
- `X-Forwarded-For`의 마지막 항목이 브라우저 IP여야 합니다. 백엔드는 마지막 항목만 로그인 시도 제한과 OMV 인증 로그에 사용합니다. 앞쪽 항목은 브라우저가 임의로 보낼 수 있으므로 쓰지 않습니다.
- 경로 접두사 아래에 둘 때는 접두사를 떼고 전달하고, 끝 슬래시가 없는 주소(`/desk`)를 `/desk/`로 리다이렉트해 주세요. 상대 경로가 `/desk/`를 기준으로 해석되기 때문입니다.
- 백엔드가 보내는 `Cache-Control`과 `ETag`를 바꾸지 말고 그대로 전달해 주세요. 이름에 해시가 붙은 `assets/` 파일은 1년 동안 캐시하고, `index.html`은 매번 다시 확인하게 해서 업그레이드 뒤 새로 고치면 새 파일을 받습니다.
- 웹 터미널은 WebSocket(`/api/terminal`)을 씁니다. 프록시가 WebSocket을 전달해야 하고, `Host` 헤더를 바꾸지 말아야 합니다. 백엔드는 다른 출처에서 연결하지 못하게 `Origin`이 `Host`와 같은지 확인합니다. 백엔드가 30초마다 ping을 보내므로 유휴 연결 제한은 그보다 길어야 합니다.
- 응답 대기 시간이 3분보다 길어야 합니다. 서비스 켜기·끄기 같은 조작은 OMV 작업이 끝날 때까지 최대 3분 동안 응답을 기다리며, 프록시가 먼저 연결을 끊으면 작업은 계속 진행되지만 화면에는 시간 초과 오류가 표시됩니다. nginx 계열 프록시는 기본값이 60초이므로 `proxy_read_timeout`을 늘려 주세요.

Caddy의 `reverse_proxy`는 기본 설정으로 이 조건을 모두 만족합니다. `X-Forwarded-Proto`와 `X-Forwarded-For`를 붙이고, `Host`를 그대로 전달하며, WebSocket을 전달하고, 응답 대기 시간에 제한이 없습니다. Caddy 앞에 다른 프록시가 없다면 `trusted_proxies`는 설정하지 마세요. 그래야 브라우저가 보낸 `X-Forwarded-For`를 Caddy가 덮어씁니다.

### Caddy 예시: OMV 기본 포트를 유지하는 경우

OMV 웹 UI가 설치할 때의 기본값대로 80번 포트(HTTP)를 쓰고 있다면, Caddy는 443번 포트(HTTPS)만 사용하게 합니다. OMV 설정은 바꾸지 않으며, OMV 웹 UI 설정(시스템 → Workbench)의 SSL/TLS는 443번 포트가 겹치지 않도록 꺼 둔 상태(기본값)여야 합니다.

Caddy는 기본적으로 80번 포트에서 HTTP를 HTTPS로 리다이렉트하므로 OMV nginx와 포트가 겹칩니다. 전역 옵션 `auto_https disable_redirects`를 주면 이 리다이렉트를 만들지 않고 80번 포트를 열지 않습니다. 따라서 `http://` 주소로 접속하면 OMV 웹 UI가 응답하고, 대시보드는 반드시 `https://` 주소로 접속해야 합니다. Caddy를 Docker로 실행한다면 443번 포트만 publish합니다.

80번 포트를 쓸 수 없으므로 HTTP-01 방식의 인증서 발급은 할 수 없습니다. 로컬 네트워크에서는 다음 중 하나를 사용합니다.

- `tls internal`: Caddy가 자체 CA로 인증서를 발급합니다. 브라우저 경고를 없애려면 Caddy의 루트 인증서(`<Caddy 데이터 디렉터리>/pki/authorities/local/root.crt`)를 접속하는 기기에 신뢰할 인증서로 등록합니다.
- DNS-01 방식: 실제로 소유한 도메인이 있다면 DNS 공급자 모듈을 포함한 Caddy로 공인 인증서를 받을 수 있습니다. 설정 방법은 Caddy 문서의 `tls` 지시어 `dns` 항목을 참고해 주세요.

서브도메인 루트에 두는 경우:

```caddyfile
{
	auto_https disable_redirects
}

dash.example.lan {
	tls internal
	reverse_proxy 127.0.0.1:8090
}
```

OMV와 같은 이름의 경로 접두사 아래에 두는 경우입니다. `https://nas.example.lan/`은 Caddy를 거쳐 OMV 웹 UI로, `https://nas.example.lan/desk/`는 대시보드로 연결됩니다. 기존 `http://nas.example.lan/`도 그대로 OMV 웹 UI에 접속됩니다.

```caddyfile
{
	auto_https disable_redirects
}

nas.example.lan {
	tls internal
	redir /desk /desk/ 308
	handle_path /desk/* {
		reverse_proxy 127.0.0.1:8090
	}
	handle {
		reverse_proxy 127.0.0.1:80   # OMV 웹 UI(기본 포트)
	}
}
```

두 예시 모두 Caddy가 호스트에서 실행되는 경우입니다. Docker 컨테이너의 Caddy라면 대시보드는 아래의 Unix 소켓 예시처럼 연결하고, OMV 웹 UI 주소는 컨테이너에서 닿는 호스트 주소로 바꿔 주세요.

### Caddy 예시: Caddy를 메인 리버스 프록시로 쓰는 경우

Caddy가 80·443번 포트를 모두 맡아 HTTPS 리다이렉트와 인증서 발급·갱신을 하고, OMV 웹 UI와 온마루를 모두 Caddy 뒤에 두는 구성입니다. 이 경우 OMV 웹 UI 설정(시스템 → Workbench)에서 OMV 포트를 다른 값으로 옮기고 SSL/TLS는 끕니다. 아래 예시에서는 `8001`로 옮겼다고 가정합니다. 온마루의 OMV 주소도 바꾼 포트에 맞춰 `http://127.0.0.1:8001`로 설정해야 합니다(설치 스크립트는 nginx 설정에서 포트를 찾아 제안합니다).

서브도메인 루트에 두고, 프록시가 호스트에서 실행되는 경우:

```caddyfile
dash.example.com {
	reverse_proxy 127.0.0.1:8090
}
```

Docker 컨테이너의 Caddy에서 Unix 소켓으로 연결하는 경우(컨테이너에 `- /run/onmaru:/run/onmaru` 볼륨을 추가해야 합니다):

```caddyfile
dash.example.com {
	reverse_proxy unix//run/onmaru/onmaru.sock
}
```

OMV와 같은 도메인의 경로 접두사 아래에 두는 경우:

```caddyfile
nas.example.com {
	redir /desk /desk/ 308
	handle_path /desk/* {
		reverse_proxy 127.0.0.1:8090
	}
	handle {
		reverse_proxy 127.0.0.1:8001   # OMV 웹 UI(옮긴 포트)
	}
}
```

## 설정 앱

"모든 앱"의 "설정", 작업표시줄 프로필 메뉴의 머리글(사용자 이름), 바탕화면 우클릭 메뉴의 "화면 설정 열기"로 엽니다. 창이 좁으면 왼쪽 메뉴가 숨고 ☰ 단추로 엽니다. 왼쪽 메뉴 맨 위의 사용자 카드를 누르면 프로필이 열립니다.

| 페이지 | 내용 | 권한 |
|---|---|---|
| 프로필 | 프로필 사진(올려서 자르기), 전자 우편과 태그(OMV 사용자 편집 화면의 Tags와 같은 값) 바꾸기, OMV 사용자 편집 화면 열기(관리자) | 모든 사용자 |
| 화면 | 테마(자동·라이트·다크), 바탕화면(기본 배경 또는 올린 이미지), 작업표시줄 아이콘 정렬(가운데·왼쪽) | 모든 사용자 |
| 일반 | 언어(이 브라우저에만 적용)와 애니메이션 | 모든 사용자 |
| 로그인 화면 | 로그인 배경과 대기 연출 켜기·끄기 | 관리자 |
| 기본 화면 | 화면 설정을 정하지 않은 사용자에게 적용할 기본 테마·바탕화면 | 관리자 |
| 서버 | 워크벤치 주소·SMART 확인 시각·웹 터미널 허용 바꾸기, 권한 도우미 상태와 root 권한 상승, 가동 설정 현황과 바꾸는 방법 | 관리자 |
| 정보 | 버전, 라이선스, 오픈 소스 고지 | 모든 사용자 |

- 관리자 페이지는 OMV 관리자 계정에만 보이며, 모든 사용자에게 적용됩니다.
- 배경 이미지는 PNG, JPEG, WebP를 20MB까지 올릴 수 있습니다. 리버스 프록시에 요청 본문 크기 제한이 있다면 20MB 이상으로 맞춰 주세요(nginx의 기본값은 1MB입니다).
- 로그인 배경은 로그인하기 전에 보이는 그림이므로, 대시보드 주소에 접속할 수 있는 누구나 볼 수 있습니다.
- 프로필의 전자 우편과 태그는 OMV 계정 정보입니다. 저장하면 OMV에 "변경 사항 적용" 대기가 생기므로, 관리자 계정은 저장할 때 적용까지 하고(OMV에 미리 적용하지 않은 변경이 있으면 저장하지 않습니다), 일반 사용자 계정은 관리자가 OMV 웹 UI에서 적용해야 합니다. OMV 기본 관리자 계정(`admin`)처럼 시스템 계정이거나 OMV에서 수정을 막은 계정은 바꿀 수 없습니다. 비밀번호·그룹 등 나머지 계정 정보는 OMV 웹 UI에서 바꿔 주세요.
- 그 밖의 OMV와 운영체제 설정은 설정 앱에서 다루지 않습니다. OMV 웹 UI에서 바꿔 주세요.
