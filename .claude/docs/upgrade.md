# 대시보드에서 업그레이드

관리자가 설정 앱의 "업데이트" 페이지에서 마루 NAS를 업그레이드한다. 설치에 쓴 로컬 git 저장소에서 새 버전을 찾고, 저장소 소유자 계정으로 빌드한 뒤 root로 설치한다. SSH로 하던 `git pull && ./install.sh`를 대신한다. 사용자 설명은 `docs/en/upgrade.md`의 "Upgrading from the dashboard"에 있고, 업그레이드 서비스가 root로 설치기를 실행하는 경로를 함께 쓰는 후속 작업은 `.claude/docs/roadmap.md`의 "웹에서 가동 설정 바꾸기"에 있다.

## 구현 위치

| 부분 | 위치 |
|---|---|
| 파일 형식(설치 기록, 업그레이드 계획, 확인·적용 요청, 상태 파일)과 서비스 상수 | `backend/config`의 `upgrade.go`, `upgrade_request.go`, `upgrade_service.go` |
| 설치기: 설치 기록, 업그레이드 계획(`--upgrade-plan`), 수동 재설치 목록 | `.claude/rules/installer.md`의 "업그레이드 계획", "수동 재설치 항목과 업그레이드 뒤 할 일" |
| 설정(`--web-upgrade`, `--build-path`), 유닛, 업그레이드 서비스(`--upgrade-service`) | `.claude/rules/installer.md`의 "업그레이드 서비스" |
| 도우미 root 연산 `upgrade.apply` | `.claude/docs/helper.md`의 "대시보드에서 업그레이드" |
| maru API(`/api/upgrade*`)와 파일 처리(`internal/upgrade`), 개발용 가짜 서비스 | `.claude/rules/backend.md`의 "대시보드에서 업그레이드" |
| 업데이트 페이지, 재시작 대기, 로그인 뒤 결과 | `.claude/rules/frontend-shell.md`의 "설정 앱" |

## 켜기

- 설치기의 `--web-upgrade` / `--no-web-upgrade`로 켜고 끈다(권한 도우미를 설치할 때만). 켜면 설치기가 저장소 경로, 빌드 계정(저장소 소유자), 1단계에서 찾은 빌드 도구의 PATH를 root 쪽 설정 파일(`/etc/default/maru-upgrade`)에 적는다. 저장소 경로는 브라우저나 maru가 정하지 않는다
- 저장소 소유자가 root이면 켤 수 없다(확인 단계에서 저장소 코드가 root로 실행되지 않게 하기 위해서다)

## 구성

- 업그레이드 서비스: root로 한 번씩 도는 systemd 유닛(`maru-upgrade.service`)과, 요청 파일을 지켜보는 `maru-upgrade.path`다. 업그레이드하면 maru와 권한 도우미가 모두 다시 시작되므로 둘 밖에서 돈다. 실행 파일은 저장소 안의 것이 아니라, 설치할 때 root 소유로 복사해 둔 설치기(`/usr/local/lib/maru/maru-install`)다
- git과 빌드는 저장소 소유자 권한으로 내려서 실행한다. 저장소에서 빌드한 코드를 root로 실행하는 것은 마지막 설치 단계(새 설치기의 `--service-install --upgrade`)뿐이며, sudo로 2단계를 실행하는 것과 같다
- 설치 기록: 설치기는 수동 설치를 포함해 설치할 때마다 버전과 커밋을 `/var/lib/maru-upgrade/installed.json`에 남긴다. `Version` 상수는 설치기도 읽을 수 있게 공개 패키지 `backend/config`에 있다
- 상태 파일: maru는 저장소를 볼 수 없으므로(`ProtectHome=yes`), 서비스가 진행과 결과를 `status.json`에 쓰고 maru는 그 파일을 읽기만 한다. 이 파일은 maru가 다시 시작되어도 남는다

## 흐름

1. 확인: 관리자가 "원격에서 가져와 확인" 또는 "로컬 저장소만 확인"을 누른다. 자동 확인은 하지 않고, 확인에는 비밀번호를 다시 묻지 않는다. 확인마다 fetch와 임시 빌드가 돌므로, 같은 방식으로 성공한 확인이 나온 지 30초가 지나지 않았으면 새로 확인하지 않고 그 결과를 보인다(실패한 확인은 바로 다시 할 수 있다). maru는 자기 상태 디렉터리에 확인 요청만 남기며, 확인 과정에서 저장소 코드는 root로 실행되지 않는다
   - 원격 확인: 소유자 계정으로 `git fetch`를 하고, 업데이트 채널의 브랜치(`origin/stable`, `origin/main`)나 채널을 고르지 않았으면 지금 브랜치의 추적 브랜치를 대상으로 삼는다. 지금 브랜치를 따르면 지금 체크아웃에서 대상으로 fast-forward할 수 있어야 한다(채널 브랜치로 옮길 때는 아래 "업데이트 채널")
   - 로컬 확인: 사용자가 SSH로 받아 둔 지금 체크아웃(HEAD)을 대상으로 삼는다. 태그를 체크아웃한 설치와 로컬 커밋도 그대로 쓸 수 있다. 작업 트리에 커밋하지 않은 변경이 없어야 하고, 설치된 커밋에서 이어진 커밋이어야 한다(되돌아가는 설치를 막기 위해서다)
2. 보여 주기: 설치된 버전과 새 버전, 그 사이의 커밋 목록, 새 버전이 묻는 설정, 업그레이드 뒤에 할 일을 보인다. 웹으로 할 수 없는 업그레이드이면 그 대신 수동 재설치 안내를 보인다
3. 업그레이드: root 권한 상승(비밀번호 재입력, 보안 강화 모드의 상승 정책 적용)을 거친다. 그 뒤 도우미의 root 연산 `upgrade.apply`가, 확인 단계에서 정한 대상 커밋과 입력한 설정 값을 요청 파일로 넘긴다. 서비스는 fast-forward, 빌드, 설치, 재시작 순서로 진행하고 단계마다 상태 파일에 진행을 쓴다
4. 다시 시작: maru가 다시 시작되면 세션이 메모리에만 있으므로 모든 세션이 끝난다. 화면은 "다시 시작하는 중"을 보이며 `/api/health`로 기다리고, 돌아오면 새로 고친다. 다시 로그인하면 업데이트 페이지가 결과를 보인다

## 업데이트 채널

- 관리자가 업데이트 페이지에서 원격 확인이 따라갈 채널을 고른다: `stable`(릴리스), `main`(개발), 빈 값(지금 브랜치의 추적 브랜치. 채널을 고르기 전과 같다). maru가 `site.json`의 `upgrade.channel`에 두고(`PUT /api/upgrade/channel`, 확인·적용이 진행 중이면 거절) 원격 확인 요청에 담는다. 로컬 확인은 채널을 쓰지 않는다
- 채널 값은 정한 셋만 받는다(`config.ValidUpgradeChannel`). 브랜치 이름을 브라우저에서 받지 않고, 원격은 `origin`(`config.UpgradeChannelRemote`)으로 고정한다
- 확인: `git fetch origin +refs/heads/<채널>:refs/remotes/origin/<채널>`로 채널 브랜치만 이름을 정해 가져와 대상으로 삼는다(브랜치 하나만 받은 클론도 된다). 지금 브랜치(`git symbolic-ref`)가 채널과 다르면 `Switch`다
  - `Switch`가 아니면 지금 브랜치를 따를 때와 같다(fast-forward 필요)
  - `Switch`면 fast-forward할 필요가 없고, 대상이 설치된 커밋에서 이어지지 않아도(main → stable처럼 이전 버전) 덮어써서 설치한다. 빠지는 커밋 수(`Dropped`, `대상..설치된 커밋`)를 화면에 알린다. 그 채널 이름의 로컬 브랜치가 있는데 대상에 포함되지 않으면(원격에 없는 커밋) 잃지 않게 `diverged`로 수동 안내한다. 이 사유는 SSH로 그 브랜치를 정리한 뒤 다시 확인하면 되므로 명령을 담지 않는다(아래 "수동 재설치 안내")
- 적용(`Switch`): 확인할 때의 브랜치와 HEAD가 그대로인지, 로컬 채널 브랜치가 아직 대상에 포함되는지 다시 본 뒤 `git checkout -B <채널> <대상>`과 `git branch --set-upstream-to=origin/<채널>`을 한다. 추적 설정이 실패하면(fetch 설정에 그 브랜치가 없는 클론) `git remote set-branches --add origin <채널>` 뒤 다시 한다. 원래 브랜치는 남는다
- 상태 파일의 `branch`·`detached`는 서비스가 마지막으로 본 브랜치다(확인할 때, 적용이 저장소를 갱신한 뒤). 화면은 이것으로 설치된 브랜치를 보이고, 저장소가 `stable`·`main`이 아니거나 아직 모르면 "지금 브랜치" 카드를 함께 보인다
- maru는 확인한 뒤 채널이 바뀌면 그 결과로 업그레이드하지 않고(`upgrade_outdated`, 화면은 결과를 숨긴다), 최근 확인 재사용(30초)도 같은 채널일 때만 한다
- 이전 버전으로 덮어쓰면 새 버전이 바꾼 상태 디렉터리 형식을 이전 버전이 읽지 못할 수 있다(자동 되돌리기를 넣지 않은 이유와 같다). 사용자에게는 확인 결과와 업그레이드 대화상자에서 알린다. 채널이 없던 버전으로 돌아가면 그 버전이 `site.json`을 다시 쓸 때 `upgrade`가 빠지고, 다시 올라오면 빈 값(지금 브랜치)이 된다
- 이전 버전의 업그레이드 서비스는 확인 요청의 채널을 모르고 지금 브랜치를 따른다. 채널이 들어간 버전으로는 그 서비스로 평소처럼 올라가고, 그때 설치기 복사본이 바뀌어 다음 확인부터 채널을 따른다. 그래서 수동 재설치 항목을 두지 않았다

## 새 설정 대응

- 새 버전의 설치기가 업그레이드 계획을 JSON으로 낸다(`--upgrade-plan`). 이 명령은 기존 설치를 읽기만 하고 아무것도 바꾸지 않는다. 확인 단계에서 대상 커밋의 설치기만 소유자 계정으로 임시 빌드해 실행하므로, 저장소를 바꾸기 전에 필요한 설정을 알 수 있다
- 기존 설치에 없는 설정과, 새 버전의 검사를 통과하지 못하는 설정은 페이지가 입력 칸으로 묻는다. 질문 문구, 기본값, 끄기(`-`)는 설치기의 설정 정의(`PromptSpec`)에서 가져온다. 설치기 문구이므로 영어와 한국어만 있다
- 입력한 값은 빌드하기 전에 새 버전의 검사(`Validate`)로 다시 확인하고, 설치기에 `--이름=값` 옵션으로 넘긴다. 계획에 나온 설정 이름만 옵션이 된다. 이미 있는 설정을 바꾸는 화면은 만들지 않는다(`.claude/docs/roadmap.md`의 "웹에서 가동 설정 바꾸기"가 할 일이다)
- 질문 방식이 특수한 설정(수신 주소처럼 `Ask`로 묻는 설정)은 웹에서 묻지 않고 수동 재설치로 안내한다

## 수동 재설치 안내

웹 업그레이드로 넘을 수 없는 변경이면 업그레이드 단추 대신 이유와 명령을 보인다.

- 새 버전이 정하는 목록: 설치기에 "설치된 버전이 이 버전보다 낮으면 수동"인 항목을 둔다. 항목에는 이유와 실행할 명령(`./install.sh` 또는 `./install.sh --reinstall`)을 적는다. 예를 들면 서비스 사용자나 소켓 경로가 바뀔 때, 권한 도우미가 처음 생겼을 때처럼 새 root 구성 요소가 생길 때, 업그레이드 서비스 자체의 동작 방식이 바뀔 때다
- 따로 정하지 않아도 수동이 되는 경우:
  - 웹에서 물을 수 없는 새 설정이 있을 때
  - 새 버전의 계획 형식을 지금 서비스가 모를 때
  - 필요한 Go·Node.js 버전(`backend/go.mod`, `frontend/package.json`의 `engines`)이 설치된 도구보다 높을 때
  - 원격 확인에서 fast-forward할 수 없을 때: 로컬 커밋이 있거나, 작업 트리에 바뀐 파일이 있거나, 추적 브랜치가 없을 때(태그를 체크아웃한 설치 포함). 이때는 로컬 확인을 쓰거나, 채널을 고르거나, 저장소를 정리하라고 안내한다
  - 채널 브랜치로 옮길 때 그 채널 이름의 로컬 브랜치에 원격에 없는 커밋이 있을 때
  - 로컬 확인에서 작업 트리에 커밋하지 않은 변경이 있거나, 대상이 설치된 커밋에서 이어지지 않을 때
  - 설치 기록이 없거나, 설치된 커밋이 저장소에 없을 때
- 보안 강화 모드처럼 새 설정 하나(`--public-origin`)로 끝나는 변경은 입력 칸으로 처리된다. 유지자가 사용자에게 문서를 꼭 읽게 하고 싶다면 그 버전을 목록에 넣어 수동으로 돌린다
- 안내 순서: 저장소 소유자 계정으로 SSH 접속 → `cd <저장소>` → 필요하면 `git pull` → `./install.sh` 또는 `./install.sh --reinstall`. 명령을 복사하는 단추를 둔다. 한 번 수동으로 올리면 그다음 버전부터는 다시 웹으로 업그레이드할 수 있다
- 사유마다 넘는 명령(`UpgradeReason.Command`)이 있고, 확인의 명령(`UpgradeCheck.Command`)은 하나라도 `--reinstall`이면 `--reinstall`, 명령이 있는 사유가 있으면 `./install.sh`다. SSH로 저장소를 정리한 뒤 다시 확인하면 되는 사유(지금은 채널 전환의 `diverged`)는 명령이 없고, 그런 사유뿐이면 확인의 명령도 비어 화면은 명령 대신 "정리한 뒤 다시 확인하세요"만 보인다

## 보안

- 업그레이드는 저장소에서 빌드한 코드를 root로 실행하므로 root 권한 상승을 거친다. 상승한 티켓으로 할 수 있는 일이 `id`에서 "설치된 저장소로 업그레이드"로 넓어지므로 사용자 문서(`docs/en/upgrade.md`의 "Security and caveats")와 도우미 설계 문서의 위협 모델에 적었다. OMV 관리자는 원래 root와 같은 일을 할 수 있으므로 새로운 권한은 아니지만, 이 기능은 끌 수 있는 선택 설정으로 둔다
- 도우미 연산은 대상 커밋(40자리 16진수)과 설정 이름·값(길이와 문자를 제한)만 받고, 명령은 받지 않는다. 채널 전환 여부는 적용 요청이 아니라 서비스가 쓴 마지막 확인에서 읽는다. 도우미 유닛에는 요청 디렉터리(`/run/maru-upgrade`)에 쓰는 권한만 더한다
- 확인 단계는 저장소 코드(대상 설치기의 계획 출력)를 소유자 권한으로만 실행한다. git을 root로 실행하지 않으므로 `safe.directory`도 건드리지 않는다
- 확인 요청은 maru가 쓰는 파일이다. 그래서 서비스는 이 파일을 심볼릭 링크를 따라가지 않고 크기를 제한해 열며, 내용을 믿지 않고 확인 방식(원격·로컬)만 읽는다
- 원격 가져오기는 소유자 계정의 git 설정과 자격 증명을 쓰며, 비밀번호를 묻지 않는다(`GIT_TERMINAL_PROMPT=0`, SSH `BatchMode`). 자격 증명이 필요하면 실패로 끝나고 안내한다

## 실패와 되돌리기

- 빌드 전이나 빌드 중에 실패하면 설치된 것은 바뀌지 않는다. 다만 원격 확인으로 진행했다면 작업 트리는 대상 커밋으로(채널을 바꿨다면 채널 브랜치로) 옮겨진 채로 남을 수 있다. 상태 파일에 실패한 단계, 오류, 로그 끝부분을 남기고, 전체 로그는 `journalctl -u maru-upgrade`에 있다
- 설치 중에 실패하면 대시보드가 뜨지 않을 수 있다. `docs/en/upgrade.md`의 "If it fails"에 SSH로 `./install.sh`를 다시 실행해 복구하는 방법을 적었다
- 자동 되돌리기는 넣지 않았다. 새 버전이 상태 디렉터리 형식을 바꿨다면 이전 버전이 그 파일을 읽지 못할 수 있기 때문이다

## 시험

- Go 테스트: 설치기는 가짜 루트와 실제 git 저장소(bare 원격 + 클론)로, maru는 임시 디렉터리와 가짜 도우미로 본다(각 규칙 문서의 "시험"·"테스트")
- 개발 서버: `make dev-fake`의 가짜 업그레이드 서비스가 시나리오(`FAKEUPGRADE_SCENARIO`)대로 상태 파일을 쓴다. 가짜 저장소는 `stable` 브랜치에서 시작해 채널을 따라 옮기고, `main`에서 `stable`로 돌아오면 이전 버전을 덮어쓰는 결과를 낸다. maru를 다시 시작하지는 않는다
- 시험 VM에서 확인한 범위: 켜기·끄기(파일, 경로 유닛, 도우미 유닛의 요청 디렉터리), 저장소 소유자로 강등한 원격 확인(fetch, 계획), 브라우저에서 업그레이드(확인 대화상자, root 권한 상승) → 진행 단계 → 설치 단계의 재시작 화면 → 새로 고침 뒤 로그인 화면 안내 → 다시 로그인하면 업데이트 페이지가 결과를 보이는 데까지. 컴파일(go·npm·make)은 미리 빌드한 실행 파일을 복사하는 shim으로 대신했다
